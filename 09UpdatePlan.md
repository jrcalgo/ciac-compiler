# CIaC v0.9 — Proof: System Verification, For Real (roadmap forecast)

> Forecast document. Assumes v0.8 (modules, blueprints, system tests,
> k8s emission) has landed, and that the v0.8-cycle external-backend
> protocol work (request/response wire contract, `ExternalBackend`, the
> `backends/go/` proof-of-concept) exists on top of it, unversioned.
> Direction-setting; the v0.9 planning pass finalizes exact flags and
> CI shape.

## The gap this version closes

v0.8 built the machinery to prove a composed system works —
`system_tests.rs` generates contract tests per cross-service edge,
`ciac verify --system` boots the real docker-compose stack, runs them,
and tears down. On paper, goal 4 ("guaranteed by the compiler") extends
to the whole system, not just each service.

In practice, none of this runs anywhere automatically. `--system` does
not appear once in CI. The one real multi-service example
(`multi-service-media.ciac`) is exercised only by diffing generated
*text* against the two built-in backends — never booted, never hit
with a real request. Docker-compose generation is duplicated,
byte-for-byte-independently, inside the Python and Rust backends' own
templates, with no shared assembly point an external backend could
ever plug into. And `--live` health probing — promised back in the
v0.6 forecast — is a stub today: `eprintln!("warning: --live health
probing is not implemented yet; running static verify")`.

**v0.9 theme: nothing in this list is a new capability. Every item
here is finishing a promise CIaC already makes in its own CLI text and
docs.** That is deliberate — a compiler whose verification story is
partially aspirational is a worse foundation for the breadth work
(v0.11) and ecosystem work (v0.12) that follow than a slower v0.9 that
closes the gap for real.

## Pillar 1 — `ciac verify --system` actually runs, automatically

- New CI job, `generated-system`, alongside the existing
  `generated-python`/`generated-rust` jobs: for every multi-service
  `project` example (today just `multi-service-media.ciac`; v0.9 adds
  at least one more so the job isn't a single-fixture proof), run
  `ciac build --target {python,rust} --out <dir>` then `ciac verify
  --system <dir>` — real `docker compose up -d --wait`, real contract
  tests, real teardown, for both hosts.
- This is additive to existing CI risk posture: `--system` already
  requires Docker and was deliberately kept out of the Docker-free unit
  `test` job (v0.8's own stated risk) — v0.9 just gives it a home
  instead of leaving it permanently unexercised.
- `ciac verify --system --keep` (new flag): skip teardown on success,
  for local debugging — the compose stack that boots stays up so a
  developer (or an agent) can poke at it after the contract tests pass.

## Pillar 2 — Real infrastructure round-trips, not just wire contracts

`system_tests.rs` today proves cross-service *edges* (a `call` reaches
its target, a publish is consumed) — it never proves a `db.insert`
actually persists, a `cache.set` actually round-trips, an
`object_store.put` actually lands in the bucket. That gap is invisible
until someone (this session, by hand) actually boots Postgres and
issues real CRUD requests.

- Extend the generated system-test suite with **capability round-trip
  assertions**: for each declared `db`/`cache`/`object_store` instance
  reachable from a generated api, one generated test that exercises
  the real verb chain end-to-end against the real dev container already
  in docker-compose (create via the api, read back through a second,
  independent client connection — proving persistence, not just
  in-process state).
- These ride the same `--system` gate as the edge tests (Docker
  required, never in unit CI) — no new infrastructure dependency
  class, just more assertions inside the same generated suite.
- Scope: reuse whatever capability instances the example already
  declares. This is not a new testing framework — it's `system_tests.rs`
  growing more assertion kinds against infrastructure it already boots.

## Pillar 3 — One system-compose assembler, not two duplicated ones

- Extract the shared parts of `system-compose.yml.j2` generation
  (service entries per capability instance, network wiring, volume
  naming) into a backend-agnostic assembler in `ciac-codegen`, called
  by both `ciac-backend-python` and `ciac-backend-rust` instead of each
  maintaining its own copy. Backend-specific pieces (the `app` service's
  `build:`/image reference) stay backend-owned.
- Golden-snapshot proof: byte-identical compose output before and
  after the refactor for every existing example — this is a pure
  dedup, not a behavior change.
- This does **not** attempt per-service backend mixing (letting one
  service in a system be generated by `python` and another by an
  external backend) — the v0.8-cycle audit found no per-service
  `--target` mechanism exists, and building one is a language/CLI
  design question orthogonal to "make the compose assembly path
  honest," not a prerequisite for it. Explicitly deferred, not solved
  here.

## Pillar 4 — `--live` health probing, implemented

- Replace the stub: after a successful `build`/`verify`, `--live` boots
  the generated compose stack (reusing Pillar 1's boot/teardown path),
  polls each service's `/health` route with a bounded timeout and
  backoff, and reports per-service up/down — the original v0.6 promise,
  finally true.

## Secondary items

- `ciac verify --system --json` (structured pass/fail per contract
  test and per capability round-trip) — small, but sets the pattern
  v0.10's structured-output work generalizes to the rest of the CLI.
- Golden coverage for the *whole* system-compose file (today only
  per-service files are snapshotted individually for multi-service
  systems; add a system-root snapshot).

## Milestones

1. System-compose assembler extraction (dedup Python/Rust compose
   generation), golden-identical proof.
2. Capability round-trip assertions added to generated system tests
   (db/cache/object_store).
3. `--live` health-probing implementation, replacing the stub.
4. `ciac verify --system --keep` flag.
5. CI: `generated-system` job; a second multi-service example added so
   the job isn't single-fixture.
6. Docs (`docs/deployment.md` verification section rewritten to match
   reality), version 0.9.0.

## Risks

- **Docker-in-CI flakiness.** Container startup time and image-pull
  reliability are real failure modes for a CI job, not just a local
  one — mitigate with generous `--wait` timeouts and retry-on-pull-
  failure, not by loosening what's actually asserted.
- **CI time budget.** Booting real Postgres/Redis/NATS per example, per
  backend, adds real wall-clock time to CI — mitigate by keeping the
  `generated-system` job to the smallest example set that still
  exercises every capability kind at least once, not every example.
- **Scope discipline.** It is tempting to fold provider breadth or
  per-service backend mixing into "verification, for real" since both
  touch the same files — both are explicitly out of scope here (v0.11
  and a future language-design pass, respectively) so this version
  stays finishable.

## After v0.9

The verification story is now true, not asserted — a passing `ciac
verify --system` in CI means what its own output claims. That's the
foundation the next two versions build on: v0.10 makes the compiler's
*output* (diagnostics, the wire protocol) legible to tools and agents
instead of just humans; v0.11 spends that trust on breadth (more
providers, real deployment targets) knowing the verification net will
catch regressions.
