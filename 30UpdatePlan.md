# CIaC v0.30-file — Generation Speed: The JVM-Per-File Tax and the Cost of Never Measuring (implementation plan)

> Implementation plan. Document number ≠ release number (standing
> precedent; expected to ship as **0.28.0**). Assumes
> 26UpdatePlan.md–29UpdatePlan.md shipped. This is the first arc in the
> project's history whose subject is the compiler's own *cost* rather
> than its behavior, and it exists because four consecutive arcs
> measured everything except how long anything took. Every prior arc
> asked "is this correct?", "is this at parity?", "does this lie?" —
> none asked "is this fast?", and the answer, discovered by accident
> while investigating a slow test suite, is that one of the five
> bundled targets has been paying a hundredfold penalty since the day
> it landed.
>
> **Parity contract:** this arc changes *no generated bytes on any
> target*. Not one line of emitted Python, Rust, TypeScript, Go, or
> Java may differ before and after. Every optimization here is a
> restructuring of *when and how many times* work happens, never of
> *what work produces*. The 145 golden snapshots
> (`tests/tests/snapshots/golden__gen__{python,rust,typescript,go,java}__*.snap`)
> are the contract's enforcement mechanism, and any milestone that
> moves one has failed, not succeeded — with exactly one disclosed
> exception, stated up front and re-stated in the milestone that could
> plausibly trigger it: nothing in this plan is expected to move a
> snapshot, and if one moves, the milestone stops and the cause is
> investigated as a defect before anything else proceeds.
>
> **Confidence:** high on the dominant fix, moderate on the long tail.
> The headline problem is measured, reproduced from a clean directory,
> root-caused to a single function, and its fix is *already
> demonstrated* — this session ran the batched invocation against real
> generated files and diffed the result byte-for-byte against the
> current per-file path (12 files, zero differences). That is not a
> hypothesis; it is a working prototype waiting to be wired in. The
> lower-confidence portion is the second half of the arc — template
> memoization, test-harness restructuring, profile tuning — where the
> gains are real but individually smaller, the interactions with
> `&dyn Backend` object safety and libtest's threading model are only
> partially explored, and the honest possibility exists that after M2
> the suite is already fast enough that M6–M7 are not worth their
> churn. The arc pre-registers that outcome as a legitimate checkpoint
> decision rather than pretending every milestone is load-bearing.

## The gap this version closes

Run this, today, on a clean checkout:

```sh
ciac build examples/order-system.ciac --target python --out /tmp/a   # 0.246s
ciac build examples/order-system.ciac --target rust   --out /tmp/b   # 0.226s
ciac build examples/order-system.ciac --target typescript --out /tmp/c # 0.185s
ciac build examples/order-system.ciac --target go     --out /tmp/d   # 0.265s
ciac build examples/order-system.ciac --target java   --out /tmp/e   # 24.168s
```

Those are measured numbers from this session's sandbox, not estimates.
Four targets finish in a quarter of a second. The fifth takes
**twenty-four seconds** — ninety-eight times longer than the median of
its peers — to emit a project of comparable size (54 files, 40 of them
`.java`).

Nothing about Java the language explains this. The Java backend's
template rendering is the same minijinja pass every other backend runs.
Its context building is the same `build_system` call. The difference is
one function:

```rust
// crates/ciac-backend-java/src/lib.rs:986
fn google_java_format(src: &str) -> Result<String, BackendError> {
    // ...
    let mut child = Command::new("java")
        .arg("--add-exports=jdk.compiler/com.sun.tools.javac.api=ALL-UNNAMED")
        // ... six more --add-exports / --add-opens ...
        .arg("-jar")
        .arg(&jar_path)
        .arg("-")            // <-- stdin -> stdout: exactly ONE file per process
        .stdin(Stdio::piped())
        .stdout(Stdio::piped())
        .stderr(Stdio::piped())
        .spawn()
```

**One JVM per generated file.** Measured cost of a single invocation:
~0.51s, essentially all of it JVM startup plus `google-java-format`
reaching into javac's internal parser and AST classes (which is why the
seven `--add-exports`/`--add-opens` flags are there). That cost does not
shrink for small files — it is a fixed per-file tax. Forty files, forty
JVMs, twenty-four seconds.

The tax compounds in three places the plan must name explicitly:

1. **`ciac build --target java`** — every build, ~24s for a flagship
   example.
2. **`ciac dev --target java`** — `crates/ciac/src/dev.rs:122`'s
   `rebuild()` calls straight into `build_inner`, so the watch loop pays
   the full tax **on every file save**. The dev loop this project shipped
   in v0.13 M4 and re-polished in 29 M2 (adding a progress line so the
   silence wouldn't confuse newcomers) is, on the Java target,
   structurally unusable as an interactive loop.
3. **The test suite** — and this is how the bug was found at all.

### How the test suite exposed it

`cargo test --workspace` takes roughly thirty to forty minutes. Four
binaries hold almost all of that:

| Binary | Wall time | `#[test]` fns | `generate()` calls |
|---|---|---|---|
| `tests/tests/determinism.rs` | **818s** | 1 | 290 (145 combos × 2, deliberate) |
| `tests/tests/conformance.rs` | **605s** | 3 | 435 (145 × 3, redundant) |
| `tests/tests/openapi.rs` | **413s** | 1 | 145 (full projects, one file read from each) |
| `tests/tests/golden.rs` | **409s** | 3 | 145 |
| **Combined** | **2,245s** | 8 | **1,015** |

The corpus is 29 `examples/*.ciac` files × 5 backends = 145
combinations, and every combination is supported — the
`check_support(...).is_err() { continue; }` guards in all four files
never actually fire, confirmed by the snapshot store holding exactly 29
`golden__gen__*` files for each of the five targets.

One fifth of those 1,015 `generate()` calls are Java. At the Java
backend's measured cost, that fifth is the overwhelming majority of the
wall time. **The test suite is not slow because it tests too much. It
is slow because it exercises a compiler bug 203 times.**

This reframing is the arc's central claim and the reason its scope is
what it is. A test-infrastructure arc — caching, parallelism, tiering —
would have made the symptom smaller while leaving every real user of
`--target java` paying twenty-four seconds a build. The fix belongs in
the compiler, and the test suite gets fast as a *consequence*, which is
both the larger win and the honest one.

### The fix is already demonstrated

The vendored jar (`crates/ciac-backend-java/vendor/google-java-format-1.19.2-all-deps.jar`,
3,602,781 bytes, `include_bytes!`-embedded at `lib.rs:970`) already
supports exactly what the backend needs. Its own `--help`, run against
the vendored artifact this session:

```
Usage: google-java-format [options] file(s)

Options:
  -i, -r, -replace, --replace
    Send formatted output back to files, not stdout.
  -
    Format stdin -> stdout
  @<filename>
    Read options and filenames from file.

If --lines, --offset, or --length are given, only one file (or -) may be given.
```

`file(s)` is plural. `-i` formats a whole list in place. `@argfile`
exists for lists longer than `ARG_MAX`. The single-file restriction
applies only to `--lines`/`--offset`/`--length`, which this backend
never passes. The current code uses `-`, the one mode that *cannot* be
batched, and has since the Java backend landed in 25UpdatePlan.md M1.

Measured, this session, against the vendored jar:

| Invocation | Wall time |
|---|---|
| 1 file, stdin mode (today's path) | **0.514s** |
| 40 files, one batched `-i` invocation | **0.805s** |
| 40 files, today's path (40 × 0.514) | **~20.6s** |

**A 25× reduction in the formatter step**, from one measurement, with no
change to the formatter, the jar, the flags, or the output.

And the output really is unchanged. This session took twelve real
generated `.java` files, mangled their formatting (stripped every
leading indent, collapsed every blank line), then formatted them two
ways — once through the current per-file stdin path, once through a
single batched `-i` invocation — and diffed the results:

```
=== files compared: 12, differing: 0 ===
```

Byte-identical. Not "equivalent", not "semantically the same": the same
bytes. That is the evidence the parity contract rests on, gathered
before the plan was written rather than promised for later.

### The three smaller gaps, found while looking

Investigating the above surfaced three further costs, each real, each
much smaller, each worth closing while the arc is open:

**No memoization exists anywhere in this repository.** A grep for
`OnceLock`, `once_cell`, `lazy_static`, `LazyLock` across all of
`crates/` returns zero hits in compiler source. Consequently every
single `generate()` call rebuilds a `minijinja::Environment` from
scratch and re-parses every embedded template:

| Backend | Templates | Bytes re-parsed per `generate()` |
|---|---|---|
| Java | 47 | 388K |
| TypeScript | 39 | 456K |
| Go | 39 | 336K |
| Rust | 39 | 256K |
| Python | 32 | 160K |

Across the slow suite's 1,015 calls that is roughly **39,000 template
parses**, all at `opt-level = 0` (there is no `[profile.test]` in the
workspace). For TypeScript — the largest template corpus and the
backend with no subprocess cost to hide behind — this is the dominant
per-call expense.

**The test harness recomputes the same corpus relentlessly.**
`tests/src/lib.rs:23`'s `compile_file` has no cache; the suite calls it
**435 times** across the same 29 files. `conformance.rs`'s three tests
each independently regenerate the identical 145 projects.
`openapi.rs` generates 145 complete projects — 30 to 100 files each —
to read exactly one file (`openapi.json`) from each and throw the rest
away.

**Two of the four slow binaries cannot parallelize at all.**
`determinism.rs` and `openapi.rs` each contain a single `#[test]` fn, so
libtest's thread pool has nothing to spread; one thread walks the whole
corpus. (`conformance.rs` and `golden.rs` have three each and do get
three-way overlap — visible in the logs, where all three conformance
tests report "running for over 60 seconds" simultaneously.)

### What this arc does not do

It does not make the suite faster by running less of it. `cargo test
--workspace` remains one complete, always-run gate; every second saved
comes from work that was genuinely wasted, never from a proof that
stopped being checked. That constraint is stated here, restated in
Pillar 5, and enforced by the arc's own exit criteria — because the
tempting version of this arc (tier the suite, gate the slow half behind
a flag, declare victory) would trade a measured engineering problem for
an unmeasured coverage problem, and this repository's entire disclosure
culture exists to prevent exactly that trade.

## Pillar 1 — Measure first, and keep measuring

The reason a hundredfold performance gap survived four arcs and five
version bumps is not that anyone dismissed it. It is that **no
instrument existed that would have shown it.** The repository has
golden snapshots (does the output match?), a negative suite (are bad
programs rejected?), an equivalence harness (do five targets agree?), a
determinism test (is generation a pure function?), a divergence ledger
(what differs, and why?), three cold-start transcripts (how does the
front door feel?) — and not one number about how long anything takes.

29UpdatePlan.md's own retrospective is instructive here: its transcripts
recorded wall-clocks for `cargo install` and for `ciac new`/`check`/
`build`, and F3 was logged as a *positive* baseline ("scaffold/check/
build messaging is already good, sub-10ms"). But every transcript ran
`--target python`. Java's twenty-four seconds sat one flag away from
three separate measurement passes and was never in frame.

So this arc's first deliverable is the instrument, built before any
optimization, exactly as 29 M1 built its baseline transcript before any
friction fix.

### `scripts/bench-codegen.sh`

A standalone script — not a `cargo test`, following the precedent of
`scripts/sim-corpus-x5.sh` and `scripts/check-deny-ignores.sh` for
things too slow or too environment-dependent for the default suite. It:

- builds `ciac` once, then for each of the 29 `examples/*.ciac` × 5
  targets, times a full `ciac build` into a scratch directory;
- reports per-(example, target) wall time, per-target totals, per-target
  medians, and the ratio of each target to the fastest;
- additionally reports, for the two formatter-shelling backends, the
  *file count* per project, so cost-per-file is derivable rather than
  guessed;
- writes a Markdown table to stdout suitable for pasting into the
  committed baseline, and exits non-zero only on a build failure (it is
  a measuring instrument, not a gate — the gate is Pillar 7's job);
- accepts `--targets python,java` and `--examples ping,order-system` so
  a developer iterating on one backend does not pay the full sweep.

The output shape matters as much as the numbers. It must be diffable:
committed as a table so that the M1→M5→M9 deltas are a `git diff`, the
same way 29's three transcripts made the front-door improvement a
reviewable artifact rather than an assertion.

### `docs/perf/codegen-baseline.md`

The committed baseline. Its opening paragraph must state the honest
caveats in the same voice 29's transcripts used — that these are
single-machine numbers from a specific sandbox with a warm cache, that
absolute values will differ on the reader's hardware, and that the
*ratios between targets on one machine* are the durable signal while
the absolute seconds are not. The document exists to make regressions
visible, not to publish a benchmark anyone should quote.

It carries, at minimum:

- the per-target table described above, at the arc's start (M1) and its
  end (M9), side by side;
- the four slow test binaries' individual wall times, before and after;
- a short "how to reproduce" section naming the script and its flags;
- a "what this does not measure" section: `ciac verify`'s downstream
  toolchain invocations (uv/cargo/tsc/go/maven), Docker-dependent paths,
  and simulation runtime — all real costs, all out of this arc's scope,
  all named so the baseline is not mistaken for a complete performance
  picture.

### The measurement discipline this arc adopts

Three rules, stated in the plan and enforced by the milestone
checklists:

1. **No optimization lands without a before number and an after number
   from the same instrument.** A milestone that improves something
   unmeasurably has not finished.
2. **The instrument runs at M1, at the M5 checkpoint, and at M9.** Three
   readings, one delta table, mirroring the transcript cadence 29
   established.
3. **A negative result is a result.** If template memoization turns out
   to save four seconds across the whole suite, the plan says four
   seconds, ships it or cuts it on that basis, and does not dress it up.
   The repository's Shipped-note tradition already does this well
   (26 M6's first-run finding triage, 27 M9's honest variance note,
   29 M5's `cargo install` regression that turned out to be cache
   state); this arc inherits it.

## Pillar 2 — The JVM-per-file tax

The dominant fix. Everything else in this arc is a rounding error
beside it.

### What exists today, precisely

`crates/ciac-backend-java/src/lib.rs`:

- **`:970`** — `GOOGLE_JAVA_FORMAT_JAR: &[u8]`, the 3.6MB jar
  `include_bytes!`-embedded into the `ciac` binary.
- **`:986`** — `google_java_format(src: &str) -> Result<String, BackendError>`,
  the per-file spawn quoted above.
- **`:1041`** — `vendored_jar_path()`, which writes the embedded jar to
  a stable path in `std::env::temp_dir()` and returns it. Already
  memoized in the weak sense that it skips the 3.6MB write when a file
  of matching *length* is present — but it performs a `metadata()`
  syscall on **every** call, and its freshness check is a length
  comparison, not a hash.
- **`:492-494`** — the `render_java` closure inside `emit_service`,
  which is simply `google_java_format(&render(name, extra)?)`.
- **39 `render_java(` call sites** inside `emit_service`, plus **one
  direct `google_java_format(...)`** at **`:424`** for the multi-service
  `system-runner/SystemSimRunner.java`.

The "39" badly understates the spawn count, and the plan must say so
plainly, because it is the difference between a fixed 39-JVM cost and
one that scales with the user's architecture. Many call sites sit inside
loops over IR collections:

| Site | Loop | Spawns |
|---|---|---|
| `:618`, `:623` | `for record in &ctx.records` / `for r_enum in &record.enums` | 1 per record + 1 per enum |
| `:707` | `for resource in &ctx.resources` (`:685`) | 1 per CRUD resource |
| `:829` | `for target in &ctx.call_targets` (`:823`) | 1 per cross-service call target |
| `:845` | `for service in &ctx.services` (`:839`) | 1 per peer service |
| `:869` | `for (name, hir) in &typed_handlers` (`:867`) | 1 per typed handler |
| `:886`/`:892`/`:901`/`:910` | workers / jobs / consumers / channels | 1 each |
| `:937` | `for api in &ctx.apis` (`:931`) | 1 per API route |

And `emit_service` itself runs once per service, from the
`for ctx in &model.services` loop at **`:377`** — so a multi-service
system multiplies the entire table again. A three-service system with a
dozen records each does not pay 39 JVM startups; it pays well over a
hundred.

Even the minimal case is bad: the `ping` fixture in the backend's own
`#[cfg(test)]` module (`:1129`) emits 8 `.java` files, so the smallest
possible Java project already spends roughly four seconds inside the
formatter.

### The design: a post-pass, not forty rewrites

The obvious fix — thread a batch accumulator through `render_java` and
flush at the end — requires touching all 40 call sites, threading
mutable state through a closure that currently returns a `String`, and
handling the `:424` direct site separately. It is invasive, it is easy
to get subtly wrong in the loop-bound sites, and it leaves the next
person who adds a 41st site free to forget.

**The recommended shape inverts it.** Let `render_java` become plain
`render` — no formatting, returning unformatted template output that
goes into the `GeneratedProject` as-is. Then, once, at the end of
`JavaBackend::generate()`, run a single post-pass:

```rust
// sketch, not final
fn format_all_java(project: &mut GeneratedProject) -> Result<(), BackendError> {
    let targets: Vec<String> = project
        .files()
        .filter(|(path, _)| path.ends_with(".java"))
        .map(|(path, _)| path.to_owned())
        .collect();
    if targets.is_empty() {
        return Ok(());
    }
    let scratch = scratch_dir()?;                       // one temp dir
    for path in &targets {
        write_flattened(&scratch, path, project.get(path).expect("listed"))?;
    }
    run_google_java_format_in_place(&scratch, &targets)?; // ONE JVM
    for path in &targets {
        project.set_content(path, read_flattened(&scratch, path)?);
    }
    Ok(())
}
```

This has four properties the call-site approach does not:

1. **It is uniform.** The 39 loop-bound sites, the `:424` direct site,
   and every future site are covered by construction, because the pass
   keys off the `.java` extension in the finished project rather than
   off who created the file.
2. **It handles multi-service for free.** `emit_service` having run N
   times is invisible to a pass that reads the assembled project.
3. **It is small.** Three lines change in `emit_service` (the
   `render_java` closure collapses into `render`), one call is added at
   the end of `generate()`, and the direct `:424` site loses its
   wrapper. Everything else is new, isolated code.
4. **It is reviewable against the parity contract.** The pass either
   produces byte-identical snapshots or it does not; there is one place
   to look.

### The pieces that need building

**A content-mutation accessor on `GeneratedProject`.** The current API
(`crates/ciac-codegen/src/project.rs:41-129`) is add-and-read only:
`add_file`, `add_seeded_file`, `add_migration_file`, `files`,
`files_with_roles`, `get`, `role`, `len`, `is_empty`, `write_to`. There
is deliberately no way to change a file's contents after insertion, and
that deliberateness deserves respect — the type's invariant ("a backend
writes each path exactly once", enforced by the `assert!(previous.is_none())`
at `:69`) is load-bearing. The new accessor must preserve it: something
shaped like `set_content(&mut self, path: &str, content: String)` that
*requires* the path to already exist and panics otherwise, keeping
"exactly once" while permitting "revised in place by a post-pass". Its
doc comment should state that it exists for formatter post-passes and
is not a general escape hatch.

**Path flattening for the scratch directory.** Generated Java paths are
nested (`svc/src/main/java/com/ciac/orders/Api.java`). Writing them into
a scratch dir either needs the directory tree recreated or the names
flattened to unique leaves. Flattening (hash or index the original path
into a `NNNN.java` name and keep a side map) avoids `mkdir -p` chains
and any chance of a path escaping the scratch root — but `google-java-format`
is a *formatter*, not a compiler, and does not resolve imports or
require the file's package to match its directory, so flattening is
safe. This should be verified explicitly at M2 rather than assumed, and
the verification recorded.

**`@argfile` fallback.** Forty paths is nowhere near `ARG_MAX`, but a
large multi-service system could pass a hundred and a pathological one
more. The jar supports `@<filename>` for exactly this. The
implementation should use the argfile unconditionally rather than
branching on a length heuristic — one code path, no threshold to get
wrong, and the argfile is written into the same scratch dir that already
needs cleaning up.

**Temp-directory lifecycle.** This is the one genuinely delicate part,
and it is delicate *because of the tests*: `cargo test` runs
`generate()` from multiple threads concurrently, so a fixed scratch path
would have concurrent Java generations trampling each other. The scratch
dir must be unique per `generate()` call (process id + a counter, or a
`tempfile`-style random suffix), and must be removed on both the success
and the error path. This is pre-registered as an open question below
because there is a real tradeoff — a reused stable dir would avoid
repeated `mkdir`/`rmdir` churn but requires locking — and the decision
should be made against measured numbers at M2, not asserted now.

**Error surfacing.** Today, a formatter failure on file *k* fails that
file's `render_java` with the formatter's stderr attached, which points
at the offending template. Batched, one bad file fails the whole
invocation, and `google-java-format`'s diagnostics reference the
*scratch* filename. The pass must map scratch names back to real
generated paths before surfacing the error, or the error message
regresses badly. A backend that emits unparseable Java is a compiler
bug, so this path should be rare — but "rare" is exactly when a
confusing error costs the most, and 29 M2/M4's findings were both about
messages that only appear when something is already going wrong.

**The `vendored_jar_path()` stat.** With one invocation per
`generate()` instead of forty, the per-call `metadata()` syscall stops
mattering. It can be left alone, and the plan should say so — the fix is
the batching, and folding an unrelated micro-optimization into the same
milestone would muddy the byte-identity review. Noted here so a reader
does not think it was missed.

### The invocation, worked

For concreteness — this is the shape the pass produces, and it is the
shape this session actually ran when proving byte-identity, so it is
known to work against the vendored jar rather than inferred from its
help text:

```sh
# today, forty times over:
java --add-exports=... -jar gjf.jar -  < Api.java  > Api.java.formatted
java --add-exports=... -jar gjf.jar -  < Dto.java  > Dto.java.formatted
# ... 38 more ...

# after: once.
printf '%s\n' /scratch/0000.java /scratch/0001.java ... > /scratch/args
java --add-exports=... -jar gjf.jar -i @/scratch/args
```

Same jar, same seven `--add-exports`/`--add-opens` flags, same version.
The only differences are `-i` instead of `-`, an argfile instead of
stdin, and one process instead of F.

The scratch layout the pass maintains alongside it:

```
/scratch/ciac-jfmt-<pid>-<n>/
    args              # the argfile, one absolute path per line
    0000.java         # flattened; maps to svc/src/main/java/com/ciac/orders/Api.java
    0001.java         # maps to svc/src/main/java/com/ciac/orders/Dto.java
    ...
```

with an in-memory `Vec<String>` (or `BTreeMap<usize, String>`) carrying
the index→real-path mapping, used both to read results back into the
right `GeneratedProject` entry and to rewrite formatter diagnostics from
`0007.java` into the generated path the user would recognize.

Flattening to indices rather than preserving the tree is deliberate:
it needs no `mkdir -p` chains, it cannot produce a path that escapes the
scratch root, and it sidesteps any question of whether two services in a
multi-service system could emit the same relative path. The one thing it
assumes — that `google-java-format` does not require a file's package
declaration to match its directory — is stated as an assumption in
Pillar 2's build list and verified explicitly at M2 rather than trusted.

### The expected result

Formatter step, flagship example: **~20.6s → ~0.8s**. Whole
`ciac build --target java`: **24.17s → low single digits**, with the
residual being template parsing (Pillar 4's target) and the ~0.25s of
real work every backend does. `ciac dev --target java` becomes an
interactive loop for the first time. The three Java-touching slow test
binaries lose the great majority of their runtime.

These are projections from measured components, and the plan should
label them as such — the M5 checkpoint exists to replace them with
readings.

### The cost model, stated parametrically

The plan should carry the arithmetic explicitly rather than asserting a
speedup, because the arithmetic is what M1's instrument will confirm or
refute, and because an implementer needs to know which quantity to
measure.

Today, for a project emitting **F** Java files:

```
t_java(F)  ≈  F × 0.51s        (formatter, one JVM each)
            + t_templates       (47 templates, 388K, re-parsed)
            + t_render          (the actual template rendering)
            + t_model           (build_system, shared with every backend)
```

After batching:

```
t_java'(F) ≈  0.80s             (formatter, ONE JVM for all F files)
            + t_templates + t_render + t_model    (unchanged)
```

So the saving per `generate()` call is approximately
**(F − 1.6) × 0.51s**, and the interesting property is that it grows
linearly with project size — the bigger the user's architecture, the
larger the win, which is the opposite of how the current code behaves.

Two sanity checks against measurements already in hand:

**The flagship.** `order-system.ciac` emits F = 40. Predicted formatter
cost 40 × 0.51 = 20.4s; measured total build 24.17s. The residual ~3.7s
is template parsing plus rendering plus model building plus process
startup — and note that the *other* backends do all of that same work in
0.19–0.27s. The gap between "3.7s of non-formatter Java work" and
"0.25s of non-formatter Python work" is not explained by the formatter
and is worth a line in M2's Shipped note: some of it is Java's larger
template corpus (388K vs 160K, Pillar 4's target), and the remainder
should be identified rather than waved at. If M2 lands and Java still
takes 3s where Python takes 0.25s, that is a second finding, not a
success.

**The suite.** The four slow binaries make 1,015 `generate()` calls,
one fifth of them Java — **203 Java generations**. Total savings
≈ 203 × (F̄ − 1.6) × 0.51s, where F̄ is the corpus-average Java file
count. Solving against the observed 2,245s combined runtime puts F̄
somewhere in the low twenties, which is plausible for a corpus whose
flagship is 40 and whose smallest (`ping`) is 8. At F̄ = 20 the
projected saving is roughly **1,900 seconds** — the great majority of
the tail.

That projection is deliberately shown with its uncertainty attached.
F̄ is not measured yet; M1's instrument is specified to report per-project
file counts precisely so this arithmetic stops being an inference. If
the real number comes in materially different, the plan's estimate was
wrong and the Shipped note says so — the fix's value does not depend on
the estimate being right, only on F̄ being greater than about two, which
it certainly is.

### What this does not fix

Batching removes the *per-file* JVM tax. It does not remove the
*per-build* one: every `ciac build --target java` still pays roughly
0.8s of JVM startup, and every `generate()` in the test suite still pays
it 203 times over. That residual — call it 160 seconds across the slow
suite — is the floor this design leaves in place, and it is the reason
the persistent-daemon idea appears in the explicit cuts rather than
being dismissed outright. If M5's measurements show that 0.8s floor
dominating what remains, the cut has a stated trigger for revisiting.

## Pillar 3 — The formatter seam, generalized

Java is not the only backend that shells out to a formatter per file.
Go does exactly the same thing, and the only reason nobody noticed is
that `gofmt` starts in two milliseconds instead of five hundred.

### Go's identical shape

`crates/ciac-backend-go/src/lib.rs`:

- **`:915`** — `gofmt(src: &str) -> Result<String, BackendError>`,
  structurally identical to `google_java_format`: one
  `Command::new("gofmt")` spawn, stdin in, stdout out, one file.
- **`:493-495`** — the `render_go` closure wrapping every `.go` render.
- **33 `render_go(` call sites**, plus two direct `gofmt(` calls at
  **`:420`** (`sim-shared/world/world.go`) and **`:433`**
  (`system-runner/main.go`), both multi-service-only.
- The same loop-bound amplification: `:758`/`:762` per resource,
  `:785` per API, `:791` per channel, `:804` per peer service, `:831`
  per typed handler, `:851`/`:857`/`:863` per worker/job/consumer,
  `:697` per call target.

Measured: **~2ms per `gofmt` invocation**, so roughly **80ms** per
project. Against Go's measured total build time of 0.265s that is real —
about thirty percent of the backend's own cost — but it is not the kind
of problem Java has, and the plan must not oversell it.

### Why fix it anyway

Three reasons, in descending order of honesty about their weight:

1. **The seam is the actual deliverable.** The bug is not "Java is
   slow"; it is "this codebase has a formatter-invocation pattern that
   is quadratic in files and nobody noticed for five releases." Fixing
   Java alone fixes an instance. Putting the batching contract in
   `ciac-codegen`, where both backends consume it, fixes the *pattern* —
   and gives the next backend that wants a real formatter (a future
   Kotlin, Swift, or C# target; `docs/external-backends.md` exists
   precisely because new targets are expected) something correct to copy
   instead of something plausible to copy.
2. **80ms is 80ms.** Across the suite's 203 Go generations that is
   ~16 seconds, and across a developer's `ciac dev --target go` session
   it is 80ms of latency per save that does not need to be there.
3. **Symmetry makes the ratchet meaningful.** Pillar 7's budget guard
   asserts that no target is wildly out of line with the others. That
   assertion is much weaker if two of the five targets are still known
   to be carrying an unfixed structural cost.

### The shared helper

A small module in `ciac-codegen` — `format_batch` or similar — carrying
the pattern once:

- takes the assembled `GeneratedProject`, an extension filter, and a
  description of how to invoke the formatter (program, fixed args, and
  whether it wants paths inline or via an argfile);
- owns the scratch-directory lifecycle, the path flattening and the
  reverse mapping, the argfile writing, and the error remapping from
  scratch names back to generated paths;
- leaves the *policy* — which program, which flags, which extension —
  with each backend, since Java's seven `--add-exports` incantations and
  Go's bare `gofmt -w` have nothing in common but their shape.

Both backends then reduce to a few lines of configuration plus one call
at the end of `generate()`. The helper is the natural home for the
`GeneratedProject::set_content` accessor's only caller, which keeps that
accessor's blast radius to one module.

### Documentation obligation

`docs/external-backends.md` describes the protocol an out-of-tree
backend speaks. It should gain a short section — two paragraphs, not a
treatise — stating that a backend which shells out to a formatter must
batch its invocations, with the measured Java number as the cautionary
example. External backends run as separate processes and cannot import
`ciac-codegen`'s helper, so the guidance has to be prose plus a worked
number rather than a shared API. That is a real limitation and the
section should say so rather than implying the helper is reusable across
the protocol boundary.

### What this pillar explicitly does not do

It does not remove the formatters. A recurring temptation — visible in
the Rust backend's own design note, which achieves canonical formatting
"implicitly via already-canonical hand-authored templates" — is to hand-
shape Java and Go templates so well that no formatter is needed. Both
backends' existing comments explain why that was rejected: no Jinja
template can reproduce a real formatter's column-width-sensitive line
wrapping, and the Java backend in particular needs Spotless's `check`
goal (bound to `verify`) to agree with what CIaC just emitted. Removing
the formatter would trade a fixed generation cost for a permanent,
open-ended template-maintenance burden and a new class of "generated
code fails its own lint gate" bugs. This is an explicit cut, restated in
the cuts section.

## Pillar 4 — Stop re-parsing every template

With the formatter tax gone, the next cost in every backend is the same
one: `generate()` builds a fresh `minijinja::Environment` and re-parses
every embedded template on every call.

### What happens today

`crates/ciac-codegen/src/template.rs:16-42`:

```rust
pub fn environment<'a>(
    templates: impl IntoIterator<Item = (&'a str, &'a str)>,
) -> Result<Environment<'a>, minijinja::Error> {
    let mut env = Environment::new();
    env.set_undefined_behavior(minijinja::UndefinedBehavior::Strict);
    env.set_keep_trailing_newline(true);
    env.add_filter("snake_case", ...);   // four casing filters, plus sqlph/ph
    ...
    for (name, source) in templates {
        env.add_template(name, source)?;   // parses and compiles, every call
    }
    Ok(env)
}
```

Each backend calls this inside `generate()` — Java at `:360`, Go at
`:365`, Python at `:125`, Rust at `:220`, TypeScript at `:692` — feeding
it every file from an `include_dir!`-embedded template directory, then
registers its own per-backend filters on top.

`add_template` eagerly parses. So a single `ciac build --target typescript`
lexes and compiles 456K of Jinja before emitting a byte, and the slow
test suite does that ~39,000 times across its 1,015 `generate()` calls,
at `opt-level = 0`.

### The constraint that makes this non-trivial

`Backend::generate` takes **`&self`** (`crates/ciac-codegen/src/lib.rs:141-168`),
and every backend is a zero-sized unit struct used as a trait object
(`&dyn Backend`, `Box<dyn Backend>`). So:

- there is no `&mut self` to stash a cache in;
- there is no field to cache *into* — `JavaBackend` is `struct JavaBackend;`;
- whatever is added must keep the trait object-safe, because
  `check_support(backend: &dyn Backend, ...)` and the `backends()`
  registry both depend on it;
- and it must be thread-safe, because the test suite calls `generate()`
  from multiple threads.

That points at a process-global `OnceLock` (or `LazyLock`) per backend
rather than per-instance state — which is fine, since the backends are
stateless singletons in practice, but it is a genuinely new pattern for
this repository: **there is currently no memoization anywhere in
`crates/`**, so this milestone introduces the codebase's first cached
global and should say so, and justify it, rather than sliding it in.

### Two candidate shapes, pre-registered

**(a) Memoize the fully-built `Environment` per backend.** Fastest —
zero per-call work. Hardest — `Environment<'a>` is lifetime-parameterized
over its template sources; a `'static` environment requires the sources
to be `'static` (they are, being `include_dir!` constants) and the
per-backend `add_filter` closures to be `'static` too (they are, being
fn pointers). The open question is whether minijinja's `Environment` is
`Sync` under the feature set in use, since a shared `&'static Environment`
rendered from many threads requires it.

**(b) Memoize only the parsed template sources / a template-name index,
and keep building a thin `Environment` per call.** Weaker win but
unambiguously safe. Falls back to this if (a) hits a `Sync` or lifetime
wall.

The plan pre-registers both and defers the choice to implementation
against the real type signatures, rather than asserting a shape that
might not compile. This mirrors how 28UpdatePlan.md pre-registered its
single-process-vs-N-process composition question and resolved it at M1–M2
with a decision matrix.

### The correctness obligation

Template memoization changes *when* templates are parsed, never what
they render. The goldens are the proof, and this milestone's exit
requires all 145 unchanged. There is one subtle trap worth naming: if
the cached environment were shared across backends, a filter registered
by one backend could leak into another's rendering namespace and change
output. The cache must therefore be **per-backend**, keyed by backend,
never a single global environment shared by all five — and the test that
proves it is simply the existing cross-target golden set, which would
show the contamination immediately.

### The expected result

Unknown, honestly, and the plan should say so. Template parsing is
pure CPU at `opt-level = 0`; a plausible range is tens of milliseconds
per call, which across 1,015 calls is meaningful but not transformative.
Pillar 1's instrument will say. If it turns out to be worth two seconds
across the whole suite, the milestone reports two seconds and the arc
moves on — the measurement is the deliverable as much as the fix is.

## Pillar 5 — Remove test redundancy without removing proofs

With the compiler fixed, what remains is the harness's own waste. This
pillar is where an arc like this most easily goes wrong, so it opens
with the constraint rather than closing with it.

### The constraint, stated first

**`cargo test --workspace` remains one complete, always-run gate.**

Not a fast tier plus a slow tier. Not a default subset with an opt-in
full run. Not an environment variable that skips the corpus sweep on
developer machines. Every second this pillar saves must come from work
that was genuinely redundant or genuinely wasteful — never from a proof
that stopped being checked.

The reasoning is not aesthetic. This repository's core product claim is
"whatever `ciac build` accepts, the generated system actually does", and
the whole apparatus that makes that claim credible — the golden set, the
equivalence suite, the determinism proof, the negative corpus, the
divergence ledger — works only because it runs unconditionally. A tiered
suite would mean that the day someone's change breaks Java's OpenAPI
byte-identity, the person who broke it does not find out; CI does, later,
maybe. Every arc from 26 onward has spent effort making claims *more*
checkable. Trading that for wall-clock would be this arc undoing four
arcs of work to fix a problem that has a real solution one pillar up.

Stated as a rule the milestone checklists can enforce: **no test is
deleted, no assertion is weakened, no `#[ignore]` is added, and the set
of properties proven after this arc is a superset of the set proven
before it.**

### The redundancy that is genuinely free to remove

**435 recompilations of 29 files.** `tests/src/lib.rs:23`'s
`compile_file` reads, parses, and analyzes from disk on every call, and
fifteen different test functions each walk the corpus independently.
Within a single test binary these are provably identical — same files,
same compiler, no mutation between calls — so a process-local cache
returning a shared `NormalizedIr` is a pure win.

The obstacles are real but small: `compile_file` returns an owned
`NormalizedIr`, and callers that want to mutate would need
`Arc<NormalizedIr>` or a clone. Most callers only read. The cache must
be keyed by path, must be per-process (test binaries do not share
memory), and — like Pillar 4's — is the repository's first memoization,
so it deserves an explicit doc comment about what it assumes (that
`examples/` does not change during a test run, which is true and worth
stating).

**`conformance.rs` generating the same 145 projects three times.** Its
three tests — `c3_openapi_is_byte_identical_across_targets`,
`c4a_migration_sql_is_byte_identical_across_targets`,
`c4b_declared_topology_appears_in_every_target` — each call a shared
`supported_projects(ir)` helper (`:49`) that regenerates every target
from scratch. The three tests prove three different properties of the
*same* generated artifacts. Computing those artifacts once and asserting
three properties over them proves exactly what it proved before, at a
third of the cost.

The tradeoff to disclose: sharing the generated set across the three
tests means they no longer run as three independent parallel tests — one
computes, or a shared lazy cache serializes the first access. Since
`conformance.rs` currently gets three-way parallelism, the arithmetic is
"1× work, serial" versus "3× work, 3-way parallel" — on a 4-core machine
those are closer than they look, and on a busy CI runner the single-work
version wins clearly. The plan should note that this one is
measurement-dependent and let M5's numbers decide whether to also split
the file.

**`openapi.rs` generating full projects to read one file.** It produces
145 complete projects — 30 to 100 files each, every template rendered,
every formatter run — to extract `openapi.json` from each and discard
the rest. What it *proves* is that every example's OpenAPI document is
well-formed and internally consistent on every target.

Two ways to make that cheap, and the choice is pre-registered: either
generate once and share with `conformance.rs`'s `c3` (which already
extracts the same file from the same projects — the overlap is exact),
or teach the test to obtain the OpenAPI document without a full project
render. The second is more invasive and risks proving something weaker
(the document as generated in isolation, rather than as it appears in a
real project), so the bias is toward the first. Whichever is chosen, the
assertion set does not shrink.

**`determinism.rs`'s double generation is NOT redundancy.** This
deserves its own paragraph because it is the single most dangerous
misreading available in this arc. The test calls `generate()` twice on
identical input and asserts byte-identical output. That second call *is
the proof*. Removing it, caching it, or sharing its result with another
test destroys the property being tested.

Worse — and this is the trap to name explicitly — **any caching
introduced by Pillars 2 or 4 could silently defeat it.** If a memoized
environment or a content-addressed formatter cache made the second
`generate()` return a stored result rather than recomputing, the test
would pass vacuously while proving nothing. The formatter batching in
Pillar 2 does not introduce such a cache (it batches within one call, it
does not cache across calls), and Pillar 4's memoization caches *parsed
templates*, not *rendered output* — but the distinction is exactly the
kind that erodes under a later well-meaning optimization. M6 should
therefore add an explicit assertion or a documented invariant that
`generate()` performs real work on every call, and the plan should carry
the reasoning so a future reader understands why an apparently wasteful
double call must stay wasteful.

### The parallelism that is free to gain

`determinism.rs` and `openapi.rs` each hold a single `#[test]` fn, so
libtest's thread pool has nothing to distribute; one thread walks 29
examples × 5 backends serially. Splitting each into per-target tests —
`generation_is_byte_deterministic_python`, `..._rust`, and so on, or a
parameterized shape — gives libtest five units to schedule instead of
one, on a machine with four cores.

This changes no assertion. The same combinations are checked; they are
merely announced to the harness as separate units. It also improves
failure reporting as a side effect: today a determinism failure says
"the corpus is non-deterministic somewhere", and after the split it says
which target.

The cost is a modest amount of boilerplate and slightly more verbose
test output. Both are acceptable. The alternative — leaving 818 seconds
of single-threaded work in place because splitting it is unglamorous —
is not.

### Binary by binary, and what remains after Pillar 2

The four slow binaries respond very differently to the compiler fix, and
the plan should say which of them M6 is actually for — because after
Pillar 2, two of them are probably fine and two are not.

**`determinism.rs` (818s, 1 test, 290 generations).** Loses the great
majority of its runtime to Pillar 2 alone, since 58 of its generations
are Java. What it does *not* lose is its single-threaded shape: whatever
remains, one thread walks it. This is the binary with the most to gain
from M6's split, and the least from any other harness change — its
double generation is a proof and its per-call work is irreducible. Split
it per target; leave everything else alone.

**`conformance.rs` (605s, 3 tests, 435 generations).** The worst
redundancy in the suite — three tests regenerating the identical 145
projects — and simultaneously the binary that already gets three-way
parallelism from that redundancy. After Pillar 2 the absolute numbers
shrink enough that the sharing-vs-parallelism tradeoff genuinely
inverts: three cheap parallel passes may beat one cheap serial pass on a
4-core machine. This is the clearest case in the arc for letting M5's
measurement decide rather than assuming, and the plan should resist the
intuition that 3× work is obviously wrong.

**`openapi.rs` (413s, 1 test, 145 generations).** Both problems at once:
single-threaded *and* generating 30–100 files per project to read one.
Pillar 2 helps; the structural waste remains. The highest-value M6
target after `determinism.rs`'s split, and the one where reuse of
conformance's already-generated set is the obvious move.

**`golden.rs` (409s, 3 tests, 145 generations).** Largely fixed by
Pillar 2, already three-way parallel, and its remaining cost is
snapshot I/O against a 28MB store — which this arc has explicitly
declined to touch absent evidence. Probably needs nothing from M6, and
M5 should be prepared to say so.

That distribution is the substance of the M5 checkpoint. If Pillar 2
takes the combined 2,245s to something in the low hundreds, then M6's
remaining value is concentrated in two changes (split `determinism.rs`,
de-waste `openapi.rs`) rather than the five listed in Pillar 5 — and
narrowing to those two would be the correct checkpoint outcome, not a
retreat from it.

### What this pillar does not touch

The 316 committed snapshots (28MB) stay. Insta's snapshot comparison is
not a measured hot spot, the snapshots are the golden contract this
whole arc is bounded by, and shrinking them would trade the arc's own
safety net for an unmeasured gain. If M5's numbers show snapshot I/O
mattering, it can be revisited; absent evidence, it is out of scope.

## Pillar 6 — Profile and runner

Two cheap, reversible levers that touch no test logic at all.

### `[profile.test]`

The workspace `Cargo.toml` carries exactly one profile setting —
`[profile.release] lto = "thin"` — and nothing for dev or test. So every
test run executes minijinja's lexer and parser, serde_json's
serializer, sha2's hasher, and heck's case conversions at
`opt-level = 0`.

For a suite whose dominant remaining work (after Pillar 2) is template
parsing and JSON serialization inside dependencies, that is a
significant self-inflicted multiplier. The standard remedy is to
optimize dependencies while leaving the crate under test unoptimized, so
debugging and backtraces are unaffected:

```toml
[profile.test.package."*"]
opt-level = 2
```

(or the `[profile.dev.package."*"]` form, since `test` inherits `dev` —
the exact spelling to be settled at implementation against the Cargo
version in use, and stated in the Shipped note.)

The tradeoff is honest and worth writing down: **the first build after
this change is slower**, because dependencies recompile optimized, and
every clean CI run pays that once. Whether it nets out positive depends
on how long the suite runs versus how long the dependency build takes,
which is exactly what Pillar 1's instrument can answer. If it does not
net out, this is cut, and the plan says so.

### The runner

`cargo test` runs test *binaries* one at a time; libtest parallelizes
the `#[test]` functions *within* each binary. The repository has 29
auto-discovered integration-test binaries under `tests/tests/`, plus 14
more under `crates/ciac/tests/`, plus per-crate suites. On a 4-core
machine, a binary containing one long test leaves three cores idle for
its entire duration.

`cargo-nextest` runs every test from every binary in a single scheduling
pool, which turns the four slow binaries from "sum of their runtimes"
into something closer to "max, bounded by cores".

Whether to adopt it is genuinely open, and the plan pre-registers it
rather than deciding now:

- **For:** it directly addresses the cross-binary serialization that
  Pillar 5's test-splitting only partially fixes; it is a well-
  maintained, widely-used tool; CI adoption is one action or one
  `cargo install`.
- **Against:** it is a new external dependency in a repository that has
  been deliberate about its toolchain surface (26 M6 added `cargo
  audit`/`cargo deny` only with a documented expiry-gate script, and
  `docs/backends.md` tracks every disclosed dependency); developers
  running plain `cargo test` would get different parallelism from CI,
  which is a divergence of exactly the kind this project's ledger
  culture dislikes; and after Pillar 2, the four slow binaries may be
  short enough that the gain is marginal.

The decision is deferred to M7, made against M5's measured numbers. If
plain `cargo test` after M2–M6 is already comfortably fast, the honest
answer is to skip nextest and say why.

### Not in scope

Sharding CI across multiple runners, caching `target/` between CI runs
beyond what already exists, or splitting the workspace into
faster-to-compile crates. All three are real levers; none is a
*generation* problem, all three add infrastructure complexity, and this
arc's thesis is that the compiler bug is the story. Named here so their
absence is a choice rather than an oversight.

## Pillar 7 — The ratchet

Every prior arc in this sequence shipped a mechanism, not just a fix.
26 shipped the divergence ledger and the audit gate. 27 shipped the
gate-emptiness tests. 28 shipped the cross-target equivalence corpus.
29 shipped the veracity harness and the transcript cadence. Each exists
so the thing that arc fixed cannot quietly un-fix itself.

This arc's mechanism is a performance ratchet, and it is needed more
than most: a hundredfold regression survived five releases precisely
because nothing was watching.

### The budget guard

A test — in the default suite, not a script — asserting that no
backend's generation cost is wildly out of line with its peers.

**It must assert a ratio, not a wall-clock.** An absolute threshold
("Java generates `ping` in under 2 seconds") is unmaintainable: it fails
on a loaded CI runner, on a slower architecture, under a debugger, and
in a container with a CPU quota, producing exactly the kind of flaky
test that gets `#[ignore]`d within a month and then proves nothing. A
ratio ("no backend takes more than N× the median backend on the same
machine, same run") is robust to machine speed because the baseline
moves with it.

Shape:

- generate one representative example on all five targets, in-process,
  timed;
- assert every target's time is within a stated multiple of the median;
- pick the multiple with real headroom — the goal is catching a return
  to *hundredfold*, not policing a 40% drift, and a tight bound would be
  flaky for no benefit;
- on failure, print the full per-target table, so the message says
  which target regressed and by how much rather than just "too slow".

The failure mode this catches is precisely the one that happened:
someone adds a formatter, a linter, a schema validator, or a subprocess
call to one backend's `generate()`, everything still passes because
every existing test only checks *output*, and the cost is invisible
until someone times a build a year later.

### The refreshed baseline

`docs/perf/codegen-baseline.md` is rewritten at M8 with the after
numbers beside the before numbers, and the M1→M9 delta table becomes the
arc's closing metric — the same role 29's 01→02→03 transcript delta
played.

### CI visibility

The generated-project CI jobs already exist. This arc adds one
lightweight thing: the benchmark script runs in CI and prints its table
to the job log. Not as a gate — a timing gate on shared runners is a
flakiness generator — but as a **visible number**, so a reviewer looking
at a PR that touched a backend can see the per-target costs without
running anything locally. The budget guard is the gate; the printed
table is the information.

### Documentation

`docs/perf/` is a new directory. It should carry the baseline plus a
short `README.md` stating what is measured, what is not, how to
reproduce, and — importantly — that the numbers are indicative rather
than authoritative. `docs/README.md`'s index (added in 29 M6) gains the
row, and `docs/external-backends.md` gains the batching guidance from
Pillar 3.

## Capability parity checklist

This arc adds no capability, no provider, no target, and no language
surface. The checklist is therefore an *invariance* checklist — the
things that must be identical after the arc as before it:

- **Generated bytes, all five targets, all 29 examples** — 145
  `golden__gen__*` snapshots unchanged. The single hardest requirement
  in the arc and the one every milestone is gated on.
- **`host_syntax_identity` snapshots (84)** — unchanged.
- **`ts_client` snapshots (29)** — unchanged.
- **`docs/targets.json`** — capability matrix unchanged (only
  `ciac_version` moves, at M9).
- **`LANGUAGE_VERSION`** — stays `1.0.0`. Nothing here touches the
  language surface, so nothing here may bump it.
- **`DESCRIBE_VERSION`** — unchanged; `ciac describe`'s output is not
  touched.
- **Simulation outcomes** — `scripts/sim-corpus-x5.sh`'s 50
  program×target combinations produce identical results. Since
  simulation runs *generated* code, and generated code is byte-identical,
  this must hold trivially — but it is verified rather than assumed,
  because "must hold trivially" is what everyone believes right up until
  it does not.
- **Diagnostics** — no new codes, no changed messages, with one
  possible exception: the Java formatter's error path (Pillar 2's error
  remapping), which must produce a message at least as useful as today's.

## Determinism and supply chain

**Determinism.** The arc's central risk to determinism is not that
output changes, but that *the proof of determinism is weakened by the
arc's own optimizations*. Three specific hazards, each with its
mitigation:

1. **Batched formatting could theoretically depend on file order.**
   `google-java-format` formats each file independently — it does not
   resolve cross-file references — so ordering should not matter. But
   "should" is not a proof, and the batch pass will iterate a `BTreeMap`
   (already sorted, since `GeneratedProject` stores files in one), which
   makes the order deterministic regardless. The determinism test then
   covers it directly.
2. **Memoization could make the second `generate()` a cache hit.**
   Discussed at length in Pillar 5. Pillar 4 caches parsed *templates*,
   not rendered *output*, so the second call still renders. The
   invariant is documented and asserted.
3. **A shared corpus cache in the test harness could hide a
   non-deterministic front-end.** `compile_file`'s cache returns the
   same IR to every caller, so a test that (hypothetically) depended on
   fresh parsing would no longer prove it. No current test does — the
   determinism proof is about *generation*, not parsing — but the cache's
   doc comment should say so, and `determinism.rs` should keep compiling
   its own IR rather than taking it from the cache, so the one test that
   is about purity does not consume a memo. This is a small deliberate
   inefficiency in service of the proof, and it should be commented as
   such so a future optimizer does not "fix" it.

**Supply chain.** The arc adds no new runtime dependency to the
compiler. The vendored `google-java-format` jar is unchanged — same
file, same bytes, same version (1.19.2), same `include_bytes!`
embedding. Nothing is downloaded at build time or run time that was not
downloaded before.

The only candidate new *tool* dependency is `cargo-nextest` (Pillar 6),
and it would be a CI-only developer tool, not a compiler or generated-
project dependency: it cannot reach the supply chain of anything CIaC
emits. If adopted, it should be pinned and noted in the same spirit as
26 M6's audit tooling. If not adopted, nothing changes.

`[profile.test]` changes optimization levels, not dependency sets.
`cargo deny` and `cargo audit` see exactly the same graph after this arc
as before it, and their CI jobs need no modification.

## Diagnostics, gating, and docs impact

**Diagnostics.** No new `CIAC####` codes. The reserved range
`CIAC0063`–`CIAC0072` (set aside in 26 M8 for a future deprecation
ladder) stays untouched — a performance arc has no business consuming
codes reserved for a language-evolution feature.

The one diagnostic surface that changes shape is the Java formatter
failure path, and it must not regress. Today a malformed template
produces a `BackendError` naming the file whose formatting failed.
Batched, the underlying tool reports scratch-directory filenames, so the
pass must map them back before surfacing. This is a correctness
requirement of the batching work, not a nice-to-have, and belongs in
M2's exit criteria.

**Gating.** No `supports()` changes, no `SimSupport` changes, no
capability gates opened or closed. `docs/targets.json`'s capability
matrix is invariant. Nothing in this arc makes a program that used to be
refused start compiling, or vice versa.

**Docs.**

- `docs/perf/codegen-baseline.md` — new, the committed baseline.
- `docs/perf/README.md` — new, scope and reproduction.
- `docs/README.md` — one index row.
- `docs/external-backends.md` — the formatter-batching section.
- `docs/backends.md` — the divergence ledger's "Open (tracked)" table
  should be checked for a row that this arc closes or that needs adding.
  Java's generation cost was never a ledger row (nothing was measuring),

## Relationship to the forecast documents

The forecast documents (19–21) sketched capability arcs — more
providers, deeper simulation, richer evolution tooling. None of them
anticipated a performance arc, and it is worth stating why rather than
implying prescience.

The forecasts were written from the question "what can't CIaC do yet?"
That question is generative for capability and blind to cost. A tool
that does the right thing slowly answers "yes, it does that" to every
forecast question, and the forecast has no follow-up. This arc exists
because a *different* question — "why is the test suite slow?" — was
asked for unrelated reasons and led somewhere the roadmap could not see.

That is the honest lineage, and it carries one forward-looking
implication worth recording in the retrospective: the forecast method
has a systematic blind spot for non-functional properties. Cost,
latency, and resource use are invisible to a capability-driven roadmap.
This arc closes the specific instance and installs a ratchet against its
recurrence, but the methodological gap is wider than the one bug, and
naming it is more useful than pretending the plan sequence saw this
coming.

Relationship to the immediately preceding arcs:

- **26UpdatePlan.md** established the disclosure culture (the two-table
  ledger, the audit gates with documented expiry) this arc's ratchet
  imitates.
- **27/28UpdatePlan.md** built the simulation depth and multi-service
  coordination that make the Java backend's cost *worse* — every service
  in a multi-service system multiplies the per-file formatter tax. Those
  arcs are not at fault; they simply made a latent quadratic more
  visible without anyone noticing.
- **29UpdatePlan.md** established measure-first discipline (the three
  cold-start transcripts) that this arc adopts wholesale, and — through
  its own veracity harness — is the reason the slow suite became
  annoying enough to investigate. It also, in its M9, hit the two
  version-derived stale artifacts (`docs/targets.json`,
  `docs/protocol-schema.json`) that this arc's M9 must handle again.

   `GeneratedProject::set_content` landed exactly as scoped: takes
   `&mut self`, panics if the path was never written (preserving

   existing only for formatter post-passes. `render_java` is now a

   a scratch directory *at its real project-relative path* (no
   index-flattening — verified live before committing to the design:
   two files with mismatched `package`/directory pairs, formatted
   together via `-i @argfile`, both came back correctly formatted;
   `google-java-format` does not care), writes one `@argfile`, runs
   one `java --add-exports=... -jar ... -i @argfile`, reads every
   file back via `set_content`, and remaps any formatter error's
   scratch paths back to real ones before returning — proven by a
   dedicated test (`format_all_java_remaps_scratch_paths_in_errors`)
   that feeds it deliberately invalid Java and asserts the error
   names the real path and never leaks the scratch directory. One
   JVM per `generate()` call confirmed by direct observation, not
   inference: `strace -f -e trace=execve` on a real `ciac build
   --target java` shows exactly one `java -jar ... -i @argfile`
   invocation for a 53-file project (the other twelve `execve`
   attempts in the trace are the shell's own `PATH` search for the
   `java` binary, not additional formatter spawns).

   **The gate caught a real bug before any snapshot was accepted.**
   The first wiring placed `format_all_java(&mut project)?` right
   after the per-service loop — before the `if model.multi` block
   that adds `system-runner/SystemSimRunner.java` to the project.
   `cargo insta test` on `golden.rs` failed immediately:
   `gen__java__audited-crud`'s snapshot showed `SystemSimRunner.java`
   completely unformatted (raw template indentation, not
   `google-java-format`'s output) because it was written to the
   project *after* the one formatting pass had already run and
   returned. Moved the call to after the multi-service block,
   immediately before `Ok(project)`; re-ran — zero pending snapshots
   across `golden.rs`, `conformance.rs`, `determinism.rs`, and
   `openapi.rs`. This is exactly the kind of defect Pillar 1's
   discipline exists to catch: a byte-identity gate that's actually
   run, not assumed, found a real ordering bug the design review
   missed, and the fix was one line moved, not a redesign.

   Also confirmed the arc's own named trap did not spring:
   `determinism.rs`'s deliberate double-`generate()` call still

   the batching is a formatting optimization, not a memoization
   layer, so it cannot mask non-determinism the way a naive
   rendered-output cache would have.

   **Shipped (v0.30 M3) — the seam generalized exactly as scoped, no
   surprises this time.** `crates/ciac-codegen/src/format_batch.rs` is
   the new home: `format_batch(project, matches, command_for)` collects
   every file matching a predicate, writes each to a scratch directory
   at its real relative path, calls `command_for(scratch, &paths) ->
   Result<Command, BackendError>` to build the invocation (the
   `Result` — a small departure from the plan's own sketch — lets a
   caller's own fallible setup, like Java's `@argfile` write or its
   vendored-jar materialization, fail cleanly instead of needing an
   `.expect()` inside a closure that can't otherwise propagate an
   error), runs it once, reads results back via `set_content`, and
   remaps scratch paths to real ones in any error — with its own two
   unit tests (`no_matching_files_is_a_no_op`, and
   `remaps_scratch_paths_in_errors`, which echoes a scratch path to
   stderr from a deliberately-failing `sh -c` command and asserts the
   real path survives while the scratch directory's name does not).
   Both backends now hold only configuration: Java's `format_all_java`
   builds the `@argfile` and the `java --add-exports=... -i @argfile`
   invocation (unchanged from M2 in substance, just relocated); Go's
   new `format_all_go` is `gofmt -w <paths...>` directly — no argfile,
   since `gofmt` takes plain positional file arguments and generated
   Go projects stay well under `ARG_MAX`. `render_go` collapsed to
   `render` the same way `render_java` did at M2 (`let render_go =
   render;`), and the two direct `gofmt(...)` call sites
   (`sim-shared/world/world.go`, `system-runner/main.go`) dropped their
   wrappers — `format_all_go` is called once, at the very end of
   `generate()`, after both the per-service loop and the multi-service
   block, learning M2's own placement lesson rather than repeating it.

   refactor, not just Go's. `c3_openapi_is_byte_identical_across_

4. **M4 — Template environment memoization.** Introduce the
   repository's first memoization. Try shape (a) — a per-backend
   `OnceLock<Environment<'static>>` — and fall back to shape (b) —
   cached parsed sources with a thin per-call environment — if
   minijinja's `Environment` turns out not to be `Sync` under the
   feature set in use, or if the `'static` lifetime cannot be satisfied
   alongside the per-backend `add_filter` registrations. Whichever
   lands, the cache is **per-backend and never shared across backends**,
   because a filter registered by one backend leaking into another's
   namespace would silently change output. All 145 goldens unchanged.
   Re-run the instrument; report the per-target delta including, if it
   is small, exactly how small. The milestone's exit does not require
   the gain to be large — it requires it to be measured and honestly
   stated.

   **Shipped (v0.30 M4) — shape (a) landed clean, and the instrument's
   own limits turned out to be the milestone's most useful finding.**
   Shape (a) worked directly: `ciac_codegen::template::
   cached_environment(cache: &'static OnceLock<Environment<'static>>,
   templates, add_filters)` builds an `Environment<'static>` once (its
   templates already borrow from each backend's `'static`
   `include_dir!` `Dir`, so no lifetime friction), registers that
   backend's filters, and stores it — no fallback to shape (b) was
   needed, and `Environment` compiled cleanly inside a `OnceLock`
   without any `unsafe`. Each of the five backends
   (python/rust/typescript/go/java) declares its own `static ENV:
   OnceLock<Environment<'static>>` at its own `generate()` call site —
   never a shared cache, so one backend's `add_filter` calls can never
   leak into another's namespace. `OnceLock::get_or_init`'s own
   documented guarantee — the initializer runs at most once, with
   concurrent callers blocking on the one in progress rather than
   racing — is what makes this safe under the test suite's own
   concurrent `generate()` calls, with no manual locking written here.
   All 145 goldens still unchanged.

   **The instrument re-run surfaced a structural limit worth stating
   plainly, not glossing over.** `scripts/bench-codegen.sh` times `ciac
   build` as a *separate process per (example, target) pair*, and
   `ciac build` calls `Backend::generate` exactly once per process
   (confirmed by inspection: one `backend.generate(&ir, &opts)` call
   site in the whole build path). A `static OnceLock` is empty at the
   start of every fresh process, so this milestone's own caching
   cannot pay for itself inside `bench-codegen.sh`'s own numbers at
   all — there is only ever one `generate()` call to memoize against
   per process, and building the environment is unavoidable overhead
   on that first (and only) call regardless of whether it's cached.
   The re-run sweep did show every target's mean drop somewhat (Java
   1.277s vs. M2/M3's 2.570s; Python 0.014s vs. M1's 0.086s) — but
   attributing that to M4 would be dishonest given the mechanism above;
   it far more plausibly reflects less concurrent system load during
   this particular run than during the M1/M2 sweeps (which ran
   alongside other heavy background test invocations in this same
   session). **Memoization's real, honest signal is only visible where
   a single process makes many `generate()` calls** — exactly what
   `determinism.rs` (290 calls), `conformance.rs` (435 calls), and
   `openapi.rs`/`golden.rs` (145 each) do. There the effect is real but
   modest, since Java's per-file formatter tax (M2's fix) was always
   the dominant cost and template parsing was always the smaller
   fraction: `determinism.rs` moved from 85.23s (post-M2/M3) to
   81.20s post-M4 — about a 5% further reduction, not a second
   headline number. `conformance.rs` stayed at 94.17s (within noise of
   its post-M3 98.88s reading). Reported exactly this way, without
   inflating the bench-codegen.sh numbers into a claim the mechanism
   doesn't support — the milestone's real product is removing genuinely
   wasted repeated parsing work in the four heaviest test binaries, a
   real if modest saving, plus the shared caching pattern now living in
   one place (`ciac_codegen::template::cached_environment`) any future
   sixth backend can reuse without re-deriving the `OnceLock` shape.
   `cargo fmt --check`/`cargo clippy --workspace --all-targets -- -D
   warnings` both clean; `template.rs`'s own 3 unit tests still pass.

   **Retrospective.**

   *What the measurement gap cost.* Four prior arcs (26-29) built
   real capability — atomicity, audit gates, simulation depth,
   multi-service coordination, a front door — on top of a compiler
   whose Java backend spent ~24 seconds generating a 40-file project
   where every other target spent a quarter of a second, and nobody
   measured it long enough to notice. The cost was not correctness
   (every one of those arcs' own golden/conformance/equivalence gates
   passed throughout) — it was attention and interactivity: a `ciac
   dev` Java save-loop nobody could use, and 2,498 seconds of `cargo
   test --workspace`'s own tail that every contributor since v0.25
   paid on every run without asking why. The fix, once found, was
   three lines moved in one function.

   *Why four arcs missed it.* Named plainly in "Relationship to the
   forecast documents" above: capability-driven roadmaps ask "what
   can't it do yet," and a slow correct answer scores identically to
   a fast one on that question. 26-29 each ran `cargo test
   --workspace` at the end of their own verification passes,
   presumably watched it take 30-40 minutes, and moved on — the number
   was visible every time, and invisible precisely because it was
   *always* visible, the same way a constant background noise stops
   registering. This arc exists because 29UpdatePlan.md's own
   veracity-harness discipline made the wait annoying enough, for
   unrelated reasons, that someone finally asked "why."

   *What the ratchet does and does not catch.* `tests/tests/
   perf_budget.rs` catches a return to the *shape* of this defect —
   any backend's generation cost drifting back toward
   hundreds-or-thousands-of-times the median, which is what one JVM
   spawn per generated file, or its equivalent in some future backend,
   would look like. It does **not** catch: a slow new capability added
   correctly to every backend uniformly (the median moves with it, so
   the ratio stays flat — by design, since a uniformly slower compiler
   is a different, real problem the relative budget cannot distinguish
   from "no problem"); a one-time regression small enough to stay under
   1000x (the multiplier is deliberately loose — see M8's own Shipped
   note for why); or anything about `ciac verify`'s downstream
   toolchain costs, Docker-dependent paths, or simulation runtime,
   none of which this instrument measures at all (named explicitly in
   `docs/perf/codegen-baseline.md`'s "What this does not measure").
   The ratchet is a smoke detector for one specific, previously-real
   fire, not a general performance monitor.

   *The forecast-method blind spot.* Stated above and repeated here
   because it is the arc's most durable finding, more durable than any
   single number in the delta table: a roadmap built entirely from
   "what can't it do yet" has no vocabulary for "it does that, but
   slowly, and nobody has measured how slowly in two years." Pillar 1
   institutionalizes measurement (`scripts/bench-codegen.sh`,
   `docs/perf/`) and M8 institutionalizes the ratchet, closing this
   specific instance. The methodological gap — that the *next* arc's
   own roadmap will again be capability-shaped, and will again have no
   eyes for a second latent cost defect growing quietly somewhere else
   in the compiler — is not closed by either of those, and is named
   here rather than implied solved.

   No git tag, no release trigger — per the standing constraint,
   raised for the user to decide separately from this arc's own
   completion. 30UpdatePlan.md is closed; there is no 31st document
   yet, and this retrospective is the handoff for whoever writes one.

## Open questions resolved at implementation (pre-registered)

1. **Memoization shape: whole `Environment` vs. parsed sources only.**
   Decided at M4 against minijinja's real type signatures — specifically
   whether `Environment` is `Sync` under the feature set in use and
   whether a `'static` environment can coexist with per-backend
   `add_filter` registration. Bias toward (a) for the larger win; (b) is
   the safe fallback and is not a failure.

2. **Scratch-directory strategy for batched formatting: unique per
   `generate()` call vs. a reused stable directory with locking.**
   Decided at M2. The forcing constraint is that test binaries call
   `generate()` concurrently from multiple threads, so a naive stable
   path is unsafe. Bias toward unique-per-call for simplicity; the
   reused variant is only worth its locking complexity if `mkdir`/
   `rmdir` churn shows up in the M2 measurement, which is unlikely at
   one directory per build.

3. **Whether `conformance.rs`'s three tests should share one generated
   set (1× work, serial) or keep regenerating (3× work, 3-way
   parallel).** Decided at M6 from M5's data. On four cores the
   arithmetic is closer than it looks, and the answer may be "share the
   set *and* split the file differently" rather than either pole.

4. **Whether `openapi.rs` can obtain its document without a full
   project render.** Decided at M6. Bias strongly toward reusing
   conformance's generated set instead, because generating the document
   in isolation would prove something weaker than "the document as it
   appears in a real generated project" — and this arc does not trade
   proof strength for speed.

5. **cargo-nextest: adopt or decline.** Decided at M7 from M5's
   numbers, not from preference. Declining with a recorded measurement
   is an acceptable and possibly likely outcome.

6. **Budget-guard threshold: which multiple of the median, and which
   example.** Decided at M8. The multiple must be loose enough to never
   flake on a loaded runner and tight enough to catch an order-of-
   magnitude regression; the example must be large enough to be
   representative and small enough that the guard is not itself a slow
   test.

7. **Whether `docs/backends.md`'s divergence ledger gains a cost
   dimension.** Raised at M8, deliberately not pre-decided. The ledger
   currently tracks capability divergence and had no vocabulary for the
   cost divergence this arc fixes — which is either a gap worth closing
   or a scope creep worth refusing, and the judgement is better made
   with the finished numbers in hand.

8. **Whether `[profile.test]` nets out positive.** Decided at M7 by
   measuring both the suite runtime improvement and the clean-build
   regression. Cut without ceremony if it does not.

## Verification strategy

The arc's verification has an unusual shape: its primary claim is a
*negative* one — that nothing changed — plus a *quantitative* one — that
it got faster. Both need oracles, and the negative claim carries far
more weight, because a performance arc that silently altered generated
output would be the worst possible outcome for a project whose entire
value proposition is that generated code is trustworthy.

The proof ledger:

| Claim | Oracle |
|---|---|
| Generated bytes are unchanged on every target | 145 `golden__gen__*` insta snapshots, zero pending after every milestone |
| Typed-handler lowering is unchanged | 84 `host_syntax_identity__*` snapshots |
| The TypeScript client is unchanged | 29 `ts_client__*` snapshots |
| Generation is still a pure function | `determinism.rs`, kept double-generating and kept off the corpus cache |
| Batched formatting equals per-file formatting | Already demonstrated pre-plan: 12 real files, mangled, both paths, byte-identical; re-proven by the goldens at M2 |
| Cross-target agreement is unchanged | `conformance.rs`'s c3/c4a/c4b; `scripts/sim-corpus-x5.sh`'s 50 combinations at M9 |
| Simulation behavior is unchanged | `sim-corpus-x5.sh` — generated code is identical, so outcomes must be; verified, not assumed |
| Java really spawns one JVM per build now | Direct observation at M2 (process counting), not inferred from wall time |
| Formatter errors still name real files | Deliberately-broken-template check at M2 |
| The suite got faster | `scripts/bench-codegen.sh` + per-binary timings, M1 vs M5 vs M9 |
| No backend silently regresses again | `perf_budget.rs`'s ratio guard, plus its own can-fail proof at M8 |
| The baseline document is reproducible | Its "how to reproduce" section, run by a reader other than its author |
| No proof was weakened to gain speed | Test-count and assertion-count comparison M1 vs M9; no `#[ignore]` anywhere |

Two verification practices carried from prior arcs deserve explicit
restatement:

**The can-fail proof.** 26 M6 proved its audit gate could fail by
feeding it a known-bad advisory; 29 M4 proved the guide harness could
fail by breaking a command block in a scratch copy. M8's budget guard
gets the same treatment: artificially slow one backend and confirm the
guard fires with a useful message. A gate never observed failing is not
known to be a gate.

**Zero pending snapshots, not reviewed diffs.** The parity contract is
checked by `cargo insta test` reporting nothing pending — not by
generating diffs and judging them acceptable. The distinction matters
because this arc's whole risk profile is "a subtle output change that
looks harmless in review". Removing human judgement from that loop is
the point.

## Milestone dependencies and parallelism

M1 must precede everything (measure first). M2 is the critical path and
depends only on M1. M3 depends on M2, since it generalizes what M2
builds — attempting the shared seam first, without a concrete second
implementation to generalize *from*, would be speculative abstraction.
M4 is independent of M2–M3 and could run in parallel with them; it is
sequenced after only because M2 is the dominant win and should not wait
behind a smaller one.

M5 is a hard gate: nothing in M6–M7 begins before the checkpoint
decision is recorded, because the checkpoint may cancel them.

M6 and M7 are independent of each other and may run in either order or
together. Both are independent of M3–M4's code paths (different files,
different concerns) but both depend on M5's authorization.

M8 depends on M2 at minimum (the ratchet is meaningless if the thing it
guards has not been fixed) and ideally on everything, since its baseline
refresh should reflect the final state. M9 depends on all of it.

The realistic critical path is therefore **M1 → M2 → M5 → M8 → M9**,
with M3, M4, M6, and M7 as parallelizable or cancellable work hanging
off it. An implementer under time pressure who did only the critical
path would still capture the overwhelming majority of the arc's value —
and the plan says so, because pretending all nine milestones are equally
load-bearing would be exactly the kind of inflation this repository's
planning tradition has avoided.

## Explicit cuts

**No pure-Rust Java formatter.** Replacing `google-java-format` with a
Rust implementation would eliminate the JVM entirely. It is also a
multi-month project to reimplement a mature formatter's exact line-
wrapping behavior, and the Java backend's generated code must satisfy
Spotless's `check` goal (bound to `verify`) — meaning any divergence
from the real formatter becomes a generated-project build failure. The
batching fix captures ~25× for a fraction of a day's work. Cut.

**No persistent formatter daemon.** Keeping one JVM alive across
`generate()` calls would help the test suite further (203 Java
generations sharing one JVM). It requires a custom wrapper jar, a
stdin/stdout protocol, process lifecycle management, and a story for
crashed daemons — substantial machinery for a win that batching already
mostly captures. Revisit only if M5's numbers show per-`generate()` JVM
startup still dominating. Cut for now, with the trigger condition
stated.

**No content-addressed formatter cache.** Caching formatted output by
source hash would make `determinism.rs`'s second `generate()` nearly
free. It would also make that test prove nothing, as discussed at length
in Pillar 5. Cut on correctness grounds, not effort grounds.

**No test tiering.** No fast/slow split, no opt-in full suite, no
environment-gated corpus sweep. Reasoning in Pillar 5. Cut on principle,
and the principle is stated so a future reader knows it was considered
and refused rather than overlooked.

**No snapshot-store reduction.** 316 snapshots at 28MB stay. Not
measured as a hot spot; they are the contract this arc is bounded by.

**No CI sharding or workspace re-splitting.** Real levers, not
generation problems, and each adds standing infrastructure complexity
for a one-time gain.

**No `ciac verify` optimization.** `verify` spends most of its time in
downstream toolchains (uv, cargo, tsc, go, maven) that CIaC does not
control. Out of scope, and named in the baseline's "what this does not
measure" section so its absence is visible.

**No simulation-runtime optimization.** `ciac sim`'s runtime cost is a
separate subject with a separate hot-path profile. This arc touches
generation only.

## Risks

**The batch pass changes generated bytes.** The single risk that would
invalidate the arc. Mitigated by the strongest available evidence
gathered *before* the plan was written — 12 real generated files,
formatting mangled, run through both paths, byte-identical — plus the
145-snapshot gate at every milestone, plus the rule that a moved
snapshot halts the milestone and is investigated as a defect rather than
accepted as an update. Residual risk: a file shape not represented among
the 12 sampled (an unusually long line, an exotic annotation) formats
differently in batch mode. The full golden set covers exactly this, and
it runs before the milestone can exit.

**Concurrency in the scratch directory.** Test binaries call
`generate()` from multiple threads; a shared scratch path would corrupt
concurrent builds in ways that might appear as flaky snapshot failures —
the worst debugging experience available here, because the symptom
(a snapshot mismatch) points at the parity contract rather than at
threading. Mitigated by unique-per-call directories as the default
choice, and by treating any nondeterministic snapshot failure during M2
as a scratch-lifecycle bug until proven otherwise.

**Memoization vacuates the determinism proof.** Discussed in Pillars 4
and 5 and in the determinism section. Mitigated by caching parsed
templates rather than rendered output, by keeping `determinism.rs` off
the corpus cache, and by documenting the real-work-per-call invariant so
a future optimizer meets the reasoning before the code.

**The arc optimizes past the point of value.** Nine milestones is a lot
for a problem whose dominant fix is one function. Mitigated structurally
by the M5 checkpoint's explicit authorization to stop, and by the
dependency section naming the critical path so partial execution is a
supported outcome rather than an abandoned arc.

**`[profile.test]` makes the common case worse.** Faster test runs but
slower clean builds; on CI, where builds are frequently clean, that can
net negative. Mitigated by measuring both sides at M7 and cutting
without ceremony if it does not pay.

**The budget guard becomes flaky and gets disabled.** The classic
failure mode of every performance test ever written: it fires on a
loaded runner, someone adds `#[ignore]`, and the ratchet silently stops
ratcheting. Mitigated by asserting ratios rather than absolute times, by
choosing a deliberately loose multiple, and by the can-fail proof
demonstrating it catches what it is for. If it flakes even once in
practice, the correct response is to loosen the bound, not to disable
the test — and that instruction belongs in the test's own doc comment,
where the person tempted to disable it will read it.

**Nothing catches the next non-functional regression.** The ratchet
guards generation cost specifically. It would not catch a memory
blow-up, a pathological compile-time regression in the compiler itself,
or a slow `ciac check`. That limitation is real, is stated in
`docs/perf/README.md`, and is the honest residue of an arc that fixes
one instance of a class.

## Confidence and handoff

**Confidence: high on the arc's headline claim, deliberately hedged on
its tail.**

The dominant fix is as well-evidenced as anything this planning sequence
has proposed. The problem is reproduced from a clean directory in five
commands. The cause is one function whose per-file spawn is visible in
five lines of source. The fix uses a mode the vendored tool already
documents in its own `--help`. The speedup is measured at 25× on the
formatter step. And the parity risk — the only thing that could make
this a bad trade — has been probed directly and came back with zero
differences across twelve real files. Very little about M2 is
speculative.

The tail is a different matter, and the plan is structured to admit it.
Template memoization might save two seconds or twenty; the harness
restructuring might be essential or might be churn; nextest might be
worth adopting or might be a dependency added out of habit. Every one of
those is written as a measured decision with a pre-registered fallback,
and M5 exists specifically so that the arc can end early with most of
its value banked rather than grinding through milestones whose
justification evaporated at M2.

The deeper handoff is methodological rather than technical. This arc
exists because a question outside the roadmap's vocabulary got asked by
accident. The forecast documents ask what CIaC cannot do; they have no
way to ask what CIaC does badly, slowly, or expensively — and a
capability-driven roadmap will keep having that blind spot after this
arc closes it in one place. The ratchet installed here watches exactly
one non-functional property of exactly one subsystem. Memory, compile
time, `ciac check` latency, simulation throughput, and the generated
projects' own build times are all unmeasured, and any of them could be
carrying a hundredfold penalty right now for exactly the reason Java's
formatter was: nothing is looking.

**Successor:** this arc hands to `31UpdatePlan.md`, and the most
defensible subject for it is the one this arc could not reach — a
systematic non-functional audit, extending the instrument built in M1
from `generate()` to the surfaces it deliberately excluded (`ciac
check`, `ciac verify`'s own overhead, simulation runtime, memory
high-water marks, and the generated projects' build times on each of the
five targets). That would convert this arc's single ratchet into a
practice.

But that recommendation is offered, not prescribed — and it is
deliberately weaker than the handoff 29UpdatePlan.md wrote. 29's
closing instruction still stands and has not been satisfied: **no
further plan file should be written until a real outside human has run
the `DOGFOODING.md` session.** This arc is the exception that proves it
rather than the precedent that overrides it. It was authorized because a
measured, reproduced, hundredfold performance defect in shipped code is
not the kind of finding that waits for a usability session — it is a
bug, found by instrumentation rather than by a user, and fixing bugs
does not require permission from a research method. A *capability* arc
would require that permission. `31UpdatePlan.md` should not be written
on the strength of this document's existence; it should be written when
either a real dogfooding session produces evidence, or another
measurement produces a defect of this arc's severity. Anything else is
planning without evidence, which 29's own last words correctly called
negative-value work.
