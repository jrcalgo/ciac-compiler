# CIaC v0.31-file — Measuring the Measurement: An Instrument That Can See the Regressions We Are About to Risk (implementation plan)

> Implementation plan. Document number ≠ release number (standing
> precedent; expected to ship as **0.29.0**). Assumes
> `26UpdatePlan.md`–`30UpdatePlan.md` shipped. This arc is the
> prerequisite the *next* arc cannot proceed without.
> `30UpdatePlan.md` established that the compiler's own cost is a
> legitimate subject, fixed the one catastrophic outlier, and left
> behind a ratchet deliberately shaped to catch that outlier
> returning. A follow-up investigation has since produced a ranked
> inventory of twelve further optimizations and mapped each one
> against the instruments that exist. **Exactly one of the twelve is
> covered.** This arc closes that gap before a single line of
> optimization lands.
>
> **Instrument-only contract:** this arc changes *no compiler behavior
> whatsoever*. Not one generated byte on any target, not one
> diagnostic code or message, not one CLI exit code, not one manifest
> field, not one line of emitted Python, Rust, TypeScript, Go, or
> Java. Every change is additive instrumentation. The single category
> of production-code edit permitted is raising an item's visibility so
> a harness can reach it (`pub(crate)` → `pub`), and each such change
> must be named in its milestone and justified in the diff. The 145
> golden snapshots
> (`tests/tests/snapshots/golden__gen__{python,rust,typescript,go,java}__*.snap`)
> plus `determinism.rs` are the enforcement mechanism, exactly as they
> were for `30UpdatePlan.md`'s parity contract: if one moves, the
> milestone stops and the cause is investigated as a defect before
> anything else proceeds. Unlike that arc, this one has no disclosed
> exception — there is no milestone here that could plausibly move a
> snapshot, and any movement at all is a bug.
>
> **Second contract — the instrument must not become the cost:** a
> benchmark suite that adds minutes to `cargo test --workspace` is a
> regression in the thing it exists to protect. This is not
> hypothetical: `perf_budget.rs` already generates the entire example
> corpus across five backends inside the default suite. Every gate
> this arc adds must either be fast enough to be invisible, or live
> behind `#[ignore]` and a dedicated CI job. M9 measures the default
> suite's wall time before and after the whole arc and reports the
> delta; a net increase beyond M1's measured noise floor is a failure
> of this arc, not an acceptable cost of it.
>
> **Confidence:** high on the instrument, moderate on the thresholds,
> deliberately low-commitment on the gates. Building a harness that
> reports trustworthy numbers is well-understood work, and the phase
> decomposition is *already prototyped* — every figure quoted in this
> document came from a throwaway version of exactly the harness M2
> specifies, run against the real corpus in a real sandbox. That is
> not a hypothesis; it is a working instrument waiting to be made
> permanent. Choosing *thresholds* that catch a 15% regression without
> firing on `ubuntu-latest`'s noise is the genuinely hard part, and
> this arc refuses to guess at it: M1 measures the noise floor first,
> and every band downstream is derived from that measurement by a rule
> pre-registered before the numbers are known. The gates themselves
> are pre-registered as droppable at the M5 checkpoint if their
> measured false-positive rate makes them liabilities. **An instrument
> nobody trusts is worse than no instrument**, because it trains
> everyone to ignore red, and this document would rather ship two
> trustworthy gates than three that get routed around.

## The gap this version closes

The investigation that motivated this arc produced twelve concrete,
located, measured optimizations. Before any of them ships, the
question that matters is: *would anything notice if they helped, and
would anything notice if they hurt?*

Run the inventory against the instruments that exist today.

| # | Optimization | `perf_budget.rs` | `bench-codegen.sh` |
|---|---|---|---|
| 1 | Lazy template loading | uniform → invisible | aggregate only, no baseline |
| 2 | Hash each generated file once, not twice | **no** — outside `generate()` | **no** — never rebuilds warm |
| 3 | Stop eager clones in the regen plan | **no** — outside `generate()` | **no** — never rebuilds warm |
| 4 | `source_hash` early-out | **no** — outside `generate()` | **no** — never rebuilds warm |
| 5 | Parallel validation | **no** | **no** — `verify` unmeasured |
| 6 | Shared `CARGO_TARGET_DIR` | **no** | **no** |
| 7 | Split `determinism.rs` for libtest | **no** | **no** |
| 8 | `[profile.dev]` tuning | **no** | **no** |
| 9 | Dedupe `build_system` | uniform → invisible | aggregate only |
| 10 | IR name/adjacency indexes | **no** — outside `generate()` | aggregate only |
| 11 | Warm/eliminate the Java formatter | **yes** — built for this | **yes** |
| 12 | Tighten the ratchet | n/a | n/a |

One of twelve. Not because the existing instruments are bad — they
are well-built and honest about their scope — but because they were
purpose-built for a different problem and never claimed to be more.

### The three structural reasons

**The gate is relative between backends.** `check_budget`
(`tests/tests/perf_budget.rs`) sorts the per-backend totals, takes the
median, multiplies by `BUDGET_MULTIPLIER`, and fails any backend over
that line. This was the right call for v0.30's problem — one backend
becoming a hundredfold outlier — and it has a property an absolute
threshold would not: it survives a slow CI runner untouched, because
every backend on a slow runner slows together and the ratios hold.

That same property is the blind spot. A change that slows every
backend by 30% produces *identical ratios* and passes silently. Items
1 and 9 are precisely that shape: `crates/ciac-codegen/src/template.rs`
and `crates/ciac-codegen/src/model.rs` are shared by all five
backends, and a regression in either moves the whole field together.

**The gate only times `generate()`.** `measure_all` brackets
`backend.generate(&ir, &GenOptions::default())` and nothing else.
Items 2, 3, 4 and 10 all live outside that call — in `ciac-syntax`,
`ciac-sema`, `ciac-ir`, or in the CLI's post-generation path through
`plan_regeneration` (`crates/ciac-codegen/src/regen.rs`) and
`build_manifest` (`crates/ciac-codegen/src/manifest.rs`). The front
end and the entire regeneration path have never been timed by
anything in this repository.

**Nothing measures a rebuild.** `scripts/bench-codegen.sh` builds into
`$WORKDIR/${name}-${target}` and `rm -rf`s it immediately after
timing. Every measurement it has ever produced is a cold build into an
empty directory. The regeneration path — which is what items 2, 3 and
4 are *about*, and which is the operation a working developer performs
hundreds of times a day through `ciac build` and `ciac dev` — is
untouched by any instrument in the repo.

### A fourth gap, in the documentation rather than the code

`docs/perf/codegen-baseline.md`'s readings table recorded
`| M9 (arc close) | pending | — | — | — |` long after M9 shipped and
closed the arc. Nothing failed; M5 stopped that arc early on the
grounds that M2–M4 had already beaten the target, M6 and M7 were both
conditional on M5 choosing to continue, and M9 closed out citing M5's
numbers rather than re-running the sweep. But the document that exists
to carry the arc's headline metric stopped describing reality the
moment the last milestone declined to measure and nobody updated the
table by hand.

That is a design lesson, not a scolding: **a metric maintained by hand
goes stale**. This arc's baseline is machine-generated, committed as
data, and diffable, precisely so that this failure mode is structurally
unavailable.

### What this arc does not do

It does not optimize anything. Not one of the twelve inventory items
is implemented here. The arc's entire output is instruments,
baselines, gates, and documentation.

This will be uncomfortable. The instrument will make several
regressions newly and obviously visible, several of which are a
one-line fix. Fixing them here is out of scope, and the temptation to
do so is a sign the instrument is working — not a license. Every
milestone's exit checklist includes a contract check for exactly this
reason.

## Pillar 1 — Thresholds come from measured noise, never from intuition

The single reason performance gates die is false positives. A gate
that fires on runner variance trains everyone to re-run CI until it
goes green, at which point it is strictly worse than absent: it costs
wall-clock time, it costs attention, and it provides no protection,
because the one time it fires for a real reason it is indistinguishable
from the nine times it did not.

`perf_budget.rs` avoids this by being relative and enormously slack: a
1000× multiplier against a 200–230× measured steady state. That is
honest — its own doc comment says plainly that it exists to catch a
return to the JVM-per-file catastrophe, "not to police ordinary
variance" — and it works. It buys its reliability by declining to
catch anything short of catastrophe, and that trade was correct for
the arc that produced it.

This arc needs to catch 15%-shaped regressions, which means the trade
has to be made differently, which means the noise has to be *measured*
rather than assumed.

M1 produces `docs/perf/noise-floor.md`: run-to-run variance for every
metric this arc intends to gate, measured both locally and on
`ubuntu-latest`, across enough repetitions to characterise the
distribution rather than merely its centre — mean, standard deviation,
min, max, and the 95th percentile, not a single number.

**The rule, pre-registered here before M1 runs:** a gate fires at
`max(3σ, 10%)` of the measured noise floor for its own metric, where σ
is the standard deviation across M1's repetitions **on the noisier of
the two environments**. If 3σ for a given metric exceeds 25%, that
metric is not gateable by wall clock at all, and must either move to
instruction counting (Pillar 2) or be dropped to reporting-only.

Recording the rule now, in this document, before the numbers exist, is
the entire point. A threshold chosen after seeing the data is a
threshold fitted to the data, and it will be chosen — consciously or
not — to make the current state pass.

## Pillar 2 — Deterministic counting over wall clock

`ubuntu-latest` is a shared, virtualised, 4-vCPU machine whose
neighbours are invisible. Wall-clock thresholds tight enough to catch a
15% regression will fire on it routinely, and several inventory items
— lazy templates, hash dedup, `build_system` dedup — sit right at that
size.

Instruction counts do not have this problem. `valgrind
--tool=callgrind` reports a count that depends on the work performed,
not on what else the machine was doing at the time. This is the model
`iai` and parts of `rustc-perf` use, and it is what makes an
*absolute*, committed baseline viable at all rather than merely
aspirational.

The costs are real and are stated here rather than discovered later:

- **Valgrind becomes a CI dependency** for exactly one job. It is
  packaged on `ubuntu-latest` (`apt-get install -y valgrind`), so this
  is an install step, not a vendoring problem.
- **10–50× slowdown under instrumentation.** A `ciac build` that takes
  12 ms takes roughly two minutes under callgrind. The gated corpus
  therefore stays small and fixed — two or three examples, not the
  full 29 — and the broad wall-clock sweep remains the informational
  instrument it already is.
- **Counts are near-deterministic, not perfectly deterministic.**
  Environment block size, ASLR, `$PWD` length, and allocator behaviour
  can all shift them slightly. This is the arc's largest technical
  uncertainty and M1 must *measure* it rather than assume it; a
  numeric threshold and a named fallback are pre-registered in the
  open questions below.

Instruction counting also delivers the allocation metric for free,
which resolves a constraint that would otherwise be awkward. The
workspace sets `unsafe_code = "forbid"` in `[workspace.lints.rust]`,
and `tests/Cargo.toml` inherits it via `[lints] workspace = true`. A
counting `#[global_allocator]` requires `unsafe impl GlobalAlloc`, and
`forbid` cannot be relaxed by an `allow` within the same crate — so the
obvious implementation would require either a new crate that opts out
of the workspace lint table, or a weakening of a lint the project has
deliberately set at its strongest level. Valgrind's DHAT tool, or
callgrind's own `_int_malloc`/`_int_free` attribution, gives
allocation totals with neither. Reusing a dependency this arc is
already taking sidesteps a lint fight, a new crate, and a precedent
nobody wants to set.

## Pillar 3 — A phase-level instrument, not a stopwatch on the whole process

`bench-codegen.sh` times `ciac build` end to end. That is the correct
outermost number and it should stay exactly as it is. But it cannot
attribute: when it moves, it does not say whether the front end, the
template environment, the hashing, or the disk writes moved, and
"something in `ciac build` got 20% slower" is not an actionable
report.

The prototype harness built during the investigation decomposed a 9 ms
`ciac build --target python` on `ping` into roughly: 3.1 ms process
startup, 1.7 ms template environment build, 0.5 ms `generate()`,
0.02 ms front end, and 3.5 ms of hashing, regeneration planning,
manifest construction and file writes. That decomposition is what made
every item on the inventory findable in the first place. M2 promotes it
from a throwaway in a scratch directory to a checked-in instrument.

Phases the harness measures, each timed independently:

| Phase | Entry point |
|---|---|
| front end — parse | `ciac_syntax::load` |
| front end — analyse | `ciac_sema::analyze` |
| LSP edit path | `ciac_syntax::module::load_with_overlay` + `analyze` |
| context model | `ciac_codegen::model::build_system` |
| semantic model | `SemanticModel::from_ir`, `.semantic_hash()` |
| generation | `Backend::generate`, per registered backend |
| template setup | first-call minus steady-state `generate()` |
| regen plan, cold | `plan_regeneration` against an empty directory |
| regen plan, warm | `plan_regeneration` against a materialised tree |
| manifest | `build_manifest` |
| write | `GeneratedProject::write_to` |
| output shape | file count, total bytes, largest single file |

The LSP row is far cheaper than its user-facing importance suggests.
`revalidate_overlay` in `crates/ciac/src/lsp.rs` does exactly
`load_with_overlay` + `ciac_sema::analyze` + `diags.sort()` +
`harvest` + `to_lsp_diagnostics` + `publish`, and
`ciac_syntax::module::load_with_overlay` is **already `pub`**. The
harness therefore measures the front-end portion — the dominant cost,
and the part the known quadratic actually hits — with no LSP client
driver, no `lsp-server` test rig, and no new public API.

`harvest` and `to_lsp_diagnostics` are private to the `ciac` binary
crate and are explicitly **excluded** from the measurement. This is
disclosed in the harness's own doc comment rather than silently
omitted, because a latency number that quietly covers 90% of a path
while being labelled as covering the path is the kind of small lie
this project's documentation conventions exist to prevent.

## Pillar 4 — A baseline that is committed, environment-stamped, and diffable

`docs/perf/codegen-baseline.md` is prose maintained by hand, and it
went stale in exactly the way prose maintained by hand does. The
replacement is `docs/perf/baseline.json`: machine-generated, committed,
versioned by a `baseline_version` integer that bumps whenever the
schema changes shape non-additively, and regenerated only through an
explicit `--update-baseline` flow so that moving it is always a
reviewable diff accompanied by a justification in the commit message.

Environment capture is not optional metadata, and this arc treats it as
load-bearing. The investigation found that the absence of SHA-NI on the
measuring machine moves SHA-256 from a modest share of a build to
**39.79% of it** — same code, same input, entirely different profile,
because `sha2` falls back to `soft::unroll::compress` rather than
dispatching to hardware. A reader who takes that 39.79% to a Zen 4 box
and cannot reproduce it will conclude the measurement was wrong. A
baseline without its environment is not merely incomplete; it actively
misleads.

Every baseline therefore stamps, at minimum: CPU model string, logical
core count, SHA-NI availability, total RAM, kernel version, `rustc` and
`cargo` versions, JDK version, Node version, Go version, Python
version, the cargo profile used, and the git SHA the reading was taken
at.

The prose document survives as the narrative layer — the M1→M5→M9
story, the "what this does not measure" section, the reproduction
instructions — and cross-links to the JSON. Its hand-maintained
readings table is retired at M9.

## Pillar 5 — Gates that catch what the current one cannot

Three gates. All land reporting-only and are promoted at M9, per the
staged-promotion decision taken for this arc.

**The uniform-regression gate (M6).** Callgrind instruction counts for
a small fixed corpus, compared against `docs/perf/baseline.json` with
the Pillar-1-derived band. This is the gate that catches items 1, 2, 3,
9 and 10 — everything the relative gate is structurally blind to. It
runs in its own CI job and is `#[ignore]`d in the default suite, so
`cargo test --workspace` is untouched.

**The asymptotic guard (M7).** A synthetic corpus at N, 2N and 4N,
asserting that growth ratios stay under a documented ceiling. This gate
is runner-independent *by construction*, because it is a ratio computed
within a single run on a single machine — it needs no noise-floor
calibration at all, which makes it the cheapest gate here and arguably
the most valuable. It catches the class "someone added an O(n²)
lookup," which no wall-clock or instruction-count threshold catches
until the corpus grows large enough to make the constant factor
visible.

`sema::analyze` is *already* at ~3.7× per doubling. The initial ceiling
is therefore set above today's measured behaviour and documented
explicitly as a ceiling to ratchet down once inventory item 10 lands —
not as a pass mark, and not as an endorsement of the current exponent.
A gate that encodes a known defect as acceptable must say so in its own
doc comment, or the next reader will take it as a target.

**The existing relative gate (kept).** `perf_budget.rs` is not
replaced. It answers a question the new gates do not — "has one backend
become an outlier relative to its peers" — and it answers it robustly
on any runner, including ones where absolute numbers are meaningless.
M9 revisits only its multiplier, now that the uniform case is covered
elsewhere.

Every new gate ships with a **harness-can-fail proof**, following the
pattern `perf_budget.rs` already establishes: `check_budget` is a pure
function separated from `measure_all` precisely so it can be unit-tested
with a synthetically slowed entry
(`fails_when_a_backend_is_artificially_slowed`). A gate that has never
been observed to fail is not known to work, and this arc extends that
discipline from a unit test to an end-to-end demonstration in CI.

## Pillar 6 — Measure the parts nobody has ever measured

Three cost centres have no instrument whatsoever, and one of them
carries the largest numbers in the entire system.

**Validation.** `ciac verify` on `order-system`, measured this
session: python 6.4 s, typescript 21.7 s, go 92.3 s, rust 308.5 s
cold. A **48× spread across targets for identical input**, essentially
all of it downstream toolchain rather than anything CIaC controls.
`docs/perf/codegen-baseline.md` lists this under "What this does not
measure" and that has been accurate since the day it was written.

M8 adds per-`ValidateStep` attribution — `npm ci` versus `tsc` versus
`eslint` versus `vitest`, not merely the total. A total tells you Rust
is slow. A breakdown tells you which step to attack, and inventory
items 5 and 6 both depend on knowing that.

**The test suite's own cost.** The four slow binaries are tracked only
as prose in the baseline document. `determinism.rs` holds exactly one
`#[test]` function, looping 29 examples × 5 backends × 2 generations,
with nothing for libtest to parallelize; `openapi.rs` likewise holds
exactly one. M8 records their timings as data rather than narrative, so
inventory item 7's effect becomes a diff.

**`ciac sim`.** Also explicitly listed as unmeasured.
`scripts/sim-corpus-x5.sh` exists but is a correctness harness — it
asserts that all five targets produce identical outcomes, not that any
of them is fast. Simulation is driven through subprocesses per target
(`sim_inner`, `crates/ciac/src/commands.rs`), so this is necessarily a
wall-clock, script-level, reporting-only metric. It is explicitly not a
callgrind candidate: instrumenting a Python interpreter running a
generated runner would measure the interpreter, not CIaC.

## Pillar 7 — Wiring, promotion, and the discipline that outlives the arc

An instrument only matters if it sits in the path of a merge. CI gains
one new job — `perf-gate`, callgrind, small corpus — and keeps the
existing informational sweep exactly as it is. M9 promotes the soaked
gates from reporting-only to blocking, updates `docs/perf/README.md`,
`docs/perf/codegen-baseline.md`, `AGENTS.md`'s build-and-test section
and `CONTRIBUTING.md`, and writes the retrospective.

The discipline this arc adopts, recorded here so the next arc inherits
it as a standing convention rather than rediscovering it:

- Any change touching a hot path names the metric it expects to move,
  and the direction, **before** the change.
- `--update-baseline` requires a justification in the commit message.
  A baseline that moves without a stated reason is a regression that
  was normalised.
- A gate that fires spuriously twice is fixed or removed — never
  widened silently. Widening is how gates die quietly rather than
  loudly.

| Contributor docs | `AGENTS.md`, `CONTRIBUTING.md` | how to run the bench, how to update a baseline |

**Production-code changes permitted by the instrument-only contract.**
Visibility raises only, and only where a harness cannot otherwise reach
a phase. A survey done while writing this plan found that every phase
in Pillar 3's table is already reachable:
`ciac_syntax::module::load_with_overlay`, `ciac_codegen::regen::plan_regeneration`,
`ciac_codegen::manifest::build_manifest`, `ciac_codegen::model::build_system`
and `SemanticModel::from_ir` are all `pub` today. **The expected count
of production-code changes in this arc is therefore zero**, and any
non-zero count is called out explicitly at M9 with its justification.

## Determinism and supply chain

This arc adds exactly one new external dependency, and it is a system
package rather than a crate: `valgrind`, installed in one CI job. No
new entries in `Cargo.toml`, no new crates in `Cargo.lock`, and
therefore no new surface for `cargo-audit` or `cargo-deny` to police —
`deny.toml` is untouched.

That is a deliberate design constraint rather than a happy accident.
The obvious alternative, `criterion`, would bring a substantial
dependency tree into a workspace that has been careful about exactly
that, in order to provide statistical wall-clock sampling — which
Pillar 2 argues is the wrong instrument for gating on a noisy shared
runner in the first place.

Determinism of the compiler itself is untouched by construction: the
instrument-only contract means no generated byte moves, and
`determinism.rs` continues to prove it. The determinism of the
*measurement* is a separate question and is the subject of M1's
callgrind drift study.

## Diagnostics, gating, and docs impact

**Diagnostics:** none. This arc registers no new `ErrorCode`, changes
no existing code's severity, title or explanation, and touches neither
`crates/ciac-diagnostics/src/code.rs` nor `docs/errors.md`. The
append-only registry is untouched, and `tests/tests/docs.rs` continues
to pass unchanged.

**Gating:** three new gates, all landing reporting-only and promoted at

**Docs:** `docs/perf/` gains two files and loses a hand-maintained

new capability divergence, so `tests/tests/ledger_integrity.rs` needs
no new row.

## Milestones

1. **M1 — The noise floor, and whether callgrind's determinism holds.**
   Measure run-to-run variance for every metric this arc intends to
   gate: locally and on `ubuntu-latest`, at least 20 repetitions,
   reporting mean, σ, min, max and the 95th percentile rather than a
   single number. Separately, establish whether callgrind instruction
   counts for `ciac build` are stable enough to gate on: repeat the
   same build at least 10 times and record the spread, then repeat
   under deliberately perturbed conditions — different `$PWD` length,
   different environment block size, ASLR disabled and enabled — and
   record the drift across those perturbations, which is the number
   that actually matters for a gate running on a machine whose
   environment nobody controls. Write `docs/perf/noise-floor.md`. Apply
   the Pillar-1 rule to produce provisional bands for M6 and M7.
   **This milestone gates every other one**: no threshold anywhere in
   this arc may be chosen before it exists. Expected to be the least
   glamorous milestone and the one every gate is answerable to —
   deliberately mirroring `30UpdatePlan.md`'s own M1, for the same
   reason.

2. **M2 — `ciac-bench`, the phase-level instrument.** New `[[bin]]` in
   `ciac-integration-tests` plus `tests/src/bench.rs`. Measures every
   phase in Pillar 3's table, per example, per backend, with warm-up
   and repetition counts derived from M1 rather than picked. Emits a
   versioned JSON document on stdout and a human-readable Markdown
   table on request (`--format=json|table`), matching the existing
   convention where `bench-codegen.sh` emits a table meant to be pasted
   into a document. Reuses the helpers already in `tests/src/lib.rs`
   rather than re-deriving corpus discovery — `ciac_files`,
   `examples_dir`, `compile_file`, `backends` all exist and are already
   the source of truth for the other test binaries. No gate and no
   baseline in this milestone: it has one job, which is to produce
   numbers trustworthy enough that a gate could later be built on
   them.

3. **M3 — The coverage the current sweep lacks.** Extend
   `scripts/bench-codegen.sh`, preserving its existing output contract
   (both CI and `docs/perf/codegen-baseline.md` reference its table
   shape, and `30UpdatePlan.md` M1 built that shape deliberately), with:
   a **warm-rebuild pass** that builds twice into the same directory and
   times the second, closing the single largest coverage hole in the
   repo; the `--deploy k8s`, `--deploy terraform`, `--deploy ci` and
   `--client ts` flag combinations, each of which invokes a generator
   and an extra `build_system` call that no instrument has ever
   exercised; generated output size, file count and largest-file size

   collects and discards; and `ciac` binary size, which `install.sh`
   users download. Add `scripts/bench-verify.sh` for per-`ValidateStep`
   attribution, kept as a separate script because it needs five

4. **M4 — The baseline: schema, environment capture, comparison.**
   Define `baseline_version` and the JSON schema in `tests/src/bench.rs`.

## Open questions resolved at implementation (pre-registered)

Recorded now, with their decision rules, so the answers cannot be
reverse-engineered from whatever turns out to be convenient.

1. **Does callgrind determinism survive this workload?** M1 answers it
   empirically. **Pre-registered threshold:** if observed drift across
   perturbed environments exceeds 2%, callgrind gating is dropped at M5
   and the fallback is same-runner merge-base comparison — run the
   benchmark twice in one CI job, once at the merge base and once at
   HEAD, and gate on the delta. That fallback costs double the
   benchmark time and buys back most of the noise immunity.

2. **Is the gated corpus two examples or three?** Decided at M6 from
   M1's measured callgrind runtime. **Rule:** if three examples push
   the `perf-gate` job beyond 10 minutes, it is two. `ping` and
   `order-system` are the fixed pair; the third is discretionary.

3. **Does `perf_budget.rs` survive M9?** Provisionally yes. It answers
   a question the new gates do not, and it is robust on runners where
   absolute numbers are meaningless. If M6's gate proves in practice to
   subsume it, M9 may retire it — but the default assumption is that
   both stay, and retiring a working gate requires an argument, not an
   omission.

4. **Where does the synthetic corpus generator live?**
   `tests/src/bench.rs`, shared between `ciac-bench` and
   `perf_scaling.rs`. Pre-registered against the temptation to let the
   gate grow a private copy — two definitions of the same fixture drift,
   and then the gate and the instrument disagree about what they are
   measuring.

5. **How long is reporting-only?** Soak is defined in **merges, not
   days**: a gate promotes to blocking after 20 merges to `main` with no
   spurious fire. If it fires spuriously once, the count resets and the
   band is re-derived from M1's data. If it fires spuriously twice, the
   gate is removed rather than widened.

6. **What happens if M2's harness cannot reproduce this document's
   phase table?** The harness is wrong, not the table — the table came
   from a working prototype of the same measurement. M2 does not exit
   until the two agree within M1's noise band.

## Verification strategy

Per milestone, the standard workspace gate: `cargo fmt --all --check`,
`cargo clippy --workspace --all-targets -- -D warnings`, and `cargo
test --workspace`.

Arc-specific, and these are the parts that actually carry the
argument:

- **The contract is mechanically checked, not asserted.** Golden
  snapshots plus `determinism.rs` prove no generated byte moved. This
  is the identical enforcement mechanism `30UpdatePlan.md` used for its
  own parity contract, and it transfers directly with no new machinery.

- **Every gate is proven to fail.** M6 and M7 each demonstrate a real
  caught regression — a deliberately slowed shared path, an
  artificially introduced quadratic — in CI, and then revert it. A gate
  that has never been observed failing is not known to work. The
  pure/impure split that `check_budget` already models is what makes
  this cheap enough to do properly rather than skip.

- **The harness is validated against known numbers.** M2's output must
  reproduce this document's phase table within M1's noise band, on
  comparable hardware. This is the only external check available on a
  new instrument, and skipping it would mean trusting a measurement
  device that has never been calibrated.

- **The arc measures its own cost.** M9 reports the default suite's
  wall-time delta across the whole arc. This is the second contract's
  enforcement, and it is a number that can fail.

- **Reproduction is documented and scripted.** Everything runs from
  `scripts/`, matching the repository's existing pattern for slow,
  environment-sensitive instruments — `bench-codegen.sh`,
  `sim-corpus-x5.sh`, `check-deny-ignores.sh` — rather than inventing a
  new convention.

## Milestone dependencies and parallelism

```text
M1 ──┬──▶ M2 ──┐
     │         ├──▶ M4 ──▶ M5 ──┬──▶ M6 ──┐
     └──▶ M3 ──┘                ├──▶ M7 ──┼──▶ M9
                                └──▶ M8 ──┘
```

M1 blocks everything, by design: no threshold anywhere in this arc may
be chosen before the noise floor exists as a committed document. M2 and
M3 are largely independent once M1 lands — M2 is in-process Rust, M3 is
shell around the built binary — and can proceed in parallel. M4 needs
both, since the baseline schema has to carry what both produce. M5 is a
hard serialization point and is meant to be. M6, M7 and M8 are mutually
independent and may proceed in any order or concurrently. M9 requires
all three plus the soak period defined at M5.

## Explicit cuts

Named so they are visibly out of scope rather than quietly missing.

- **Peak RSS / memory-high-water gating.** Callgrind's allocation
  attribution covers most of the value at no additional dependency. A
  real memory gate needs its own harness, its own noise
  characterisation, and its own false-positive budget. Deferred, not
  rejected.

- **A `criterion` dependency.** Its statistical machinery is built for
  microbenchmarks with wall-clock sampling — precisely the regime
  Pillar 2 argues against for gating on a shared runner. Adding it
  would import a large dependency tree into a workspace that has been
  careful about exactly that, to solve a problem instruction counting
  solves better here.

- **Historical time-series storage and a dashboard.**
  `docs/perf/baseline.json` plus git history *is* the time series. A
  service to plot it is a different project with different
  requirements.

- **External-backend protocol overhead.** The subprocess spawn and JSON
  round-trip in `crates/ciac-codegen/src/external.rs` stays unmeasured.
  It is a niche path and no inventory item touches it.

- **Per-keystroke LSP driving through a real client.** M8 measures the
  front-end portion, which is the dominant cost and the part the
  quadratic hits. A full `lsp-server` test rig is disproportionate to
  the marginal signal.

- **Optimizing anything.** Restated as a cut because it is by some
  distance the likeliest scope breach: the twelve inventory items are
  the *next* arc, and this one ends without touching them.

## Risks

**The gates are calibrated on the wrong machine.** M1 measures both
locally and on `ubuntu-latest` specifically because the two differ, and
the Pillar-1 rule takes the noisier of the two. Residual risk remains
if GitHub changes runner characteristics mid-arc — mitigated by the
soak rule, which surfaces drift as spurious fires and forces
re-derivation from data rather than silent widening.

**Callgrind determinism does not hold.** Pre-registered as open
question 1 with a numeric threshold and a named fallback. This is the
arc's largest technical uncertainty, and it is deliberately answered in
the first milestone rather than discovered in the sixth, when three
milestones of work would already depend on it.

**The arc slows the default test suite.** The second contract exists
for exactly this, and M9 measures it rather than assuming it.
Mitigation is structural rather than procedural: gates live in a
dedicated CI job and are `#[ignore]`d locally.

**Scope creep into optimization.** The instrument will make several
regressions newly visible and several of them are one-line fixes. Every
milestone's exit checklist includes the contract check, and "Explicit
cuts" names this as the likeliest breach so that a reviewer knows to
look for it.

**The baseline goes stale exactly as the prose table did.** Mitigated
by machine generation, by `--update-baseline` requiring a written
justification, and by M9 removing the hand-maintained table that failed
this way — the failure mode is designed out rather than guarded
against.

**A gate is added that nobody trusts.** The soak rule and the
two-strikes removal rule are the mitigation, and they are deliberately
harsher than the industry-standard response of widening the band. A
removed gate is an honest signal; a gate widened until it cannot fire
is a false one.

## Confidence and handoff

**High confidence in M1–M4.** Measuring variance, decomposing phases
into a harness, and defining a committed baseline schema are
well-understood work with no unexplored interactions. The phase
decomposition is already prototyped: every number in this document came
from a throwaway version of the M2 harness, run against the real corpus.
M2 is a promotion, not an invention.

**Moderate confidence in M6–M8**, and the uncertainty is concentrated
almost entirely in threshold selection rather than implementation. The
code is straightforward; the judgement about which band catches real
regressions without firing on noise is not, which is exactly why M1
precedes it and M5 exists to abandon gates that fail that test.

**Deliberately low commitment to shipping all three gates.** M5
pre-registers dropping any of them as a legitimate, successful outcome.
The arc's real deliverable is the *instrument* — the phase harness, the
committed baseline, and coverage of paths nothing has ever timed. The
gates are the portion that has to earn its place against a
false-positive budget, and this document would rather ship two
trustworthy gates than three that get routed around.

**The handoff to the next arc is concrete rather than aspirational.**
With `docs/perf/baseline.json` committed and the phase harness in
place, each of the twelve inventory items becomes a before/after diff
against a named metric with a stated expected direction — the table in
"Relationship to the optimization inventory" above is that handoff,
written in advance. The next arc opens by running `ciac-bench
--compare` and closes by running it again, and the difference between
those two runs is its entire claim.

## Retrospective

Executed in one continuous session (M1 through M9, commits `f7ec595`
through the version-bump commit closing this one), with the three
tensions between the plan's literal text and single-session execution
resolved up front and honored throughout: no gate soaked through a
real 20-merge history and none was promoted; CI noise sampling stayed
local-heavy plus one diagnostic job rather than a dedicated polling
campaign; every milestone ran inline with its own review checklist
rather than through subagent delegation. All nine milestones shipped;
none was cut.

**What the instrument found that the motivating investigation missed.**
Four findings this session's own measurement work surfaced that the
earlier informal assessment did not:

1. `perf_budget.rs`'s own doc comment quoted Java at "~200-230x the
   median backend" as its calibration figure. M9's revisit measured
   this live and found that figure only holds in the debug profile
   `cargo test --workspace` actually runs the gate under
   (131.7x-187.4x observed across three runs) — under `--release`, the
   same backends produce a misleadingly tight ~950-1010x ratio, because
   Java's JVM-spawn cost is profile-invariant while the cheap backends'
   own in-process cost collapses under optimization. A naive revisit
   that measured with `--release` (the profile every other wall-clock
   number in this arc uses) would have concluded the gate needed
   tightening; it does not, because that is not the profile it runs
   under. This was caught only because the revisit measured the actual
   gating condition rather than trusting the doc comment's own
   arithmetic.
2. Local sandbox wall-clock noise measured *higher* than real
   `ubuntu-latest` noise (68.1% vs. 11.6% relative standard deviation,
   `noise-floor.md`'s own whole-process comparison) — the opposite of
   the usual assumption that a shared CI runner is the noisier
   environment. Session-level contention in this sandbox dominates
   over CI's own scheduling variance.
3. Callgrind's determinism (0.00079%-0.00653% drift across two
   unrelated machines and every perturbed condition tried) is far
   tighter than the pre-registered `max(3σ, 10%)` rule's `10%` floor
   would have allowed for — applied literally, that floor would have
   produced a gate that only fires on a tenfold regression, redundant
   with `perf_budget.rs`. The 150x-multiplier deviation
   (`noise-floor.md`'s own "Gate decisions" section) exists because
   this was measured rather than assumed.
4. `sema::analyze`'s growth on this session's own synthetic corpus
   (1.93x-2.80x per doubling, trending upward with N) came in
   measurably below the ~3.7x/doubling the motivating investigation
   found on a differently-shaped corpus — same underlying quadratic,
   a different exponent depending on what the corpus actually
   exercises. "How bad is the quadratic" turned out not to be a single
   portable number, which is itself the reason
   `SEMA_ANALYZE_GROWTH_CEILING`'s own doc comment states the specific
   corpus and reps it was calibrated against rather than citing the
   motivating investigation's figure as if it travels.

**What the arc cost.** In CI minutes: the one real-CI sample this arc
captured directly, `perf-gate`'s own run (`31364165785`, job
`93378885978`), completed in 3m04s (07:00:55-07:03:59), non-blocking
via step-level `continue-on-error`. `perf-noise-floor` runs one
20-repetition wall-clock sweep plus a 5-repetition callgrind sample
per push, also non-blocking. Neither adds to the required-to-merge
critical path; both print into the job summary. In session time: nine
milestones, each with a full review checklist (fmt, clippy, the full
test suite, an instrument-only diff check, snapshot stability), plus
the M6 CI round-trip demonstration and the M9 second-contract timing
(which needed three attempts before landing a clean, uncontaminated
number — see below).

**Which gates were dropped, and which weren't.** None. M5's checkpoint
reached pre-registered outcome (a) — "proceeds" — for both new gates
individually: the uniform-regression gate (M6, callgrind) and the
asymptotic guard (M7, ratio-based) both shipped. The checkpoint's
*overall* character is closer to outcome (b) in a different sense than
"a gate got dropped": every wall-clock measurement this arc produces
(the phase table, every `generate()` figure, whole-process build
timings) is declared **permanently** reporting-only, not merely
pending a soak — M1's own noise-floor numbers make every wall-clock
metric fail the pre-registered 25% gateability ceiling outright, so
there is no threshold at which those numbers were ever going to become
a pass/fail gate. That is a stronger, permanent statement than "not
yet promoted," and it is the correct one: `perf_budget.rs`'s own
relative-ratio design was already the answer to wall-clock noise this
arc could not improve on, not a gap this arc left unfilled.

**Whether the pre-registered thresholds survived contact with real
data.** Mostly yes, with one named exception. The Pillar-1 rule
(`max(3σ, 10%)`) survived for wall-clock metrics exactly as written —
every one of them failed the 25% ceiling, precisely the outcome the
rule was designed to detect and refuse to gate on. It did **not**
survive unmodified for instruction-count metrics: the `10%` floor was
replaced by a 150x multiplier over observed drift, disclosed as a
deviation rather than silently applied (`noise-floor.md`'s own
section, referenced above). The asymptotic guard's ceilings
(`SEMA_ANALYZE_GROWTH_CEILING = 4.5`, `GENERATE_GROWTH_CEILING = 3.0`)
were set from this session's own measurement rather than the
motivating investigation's figures, for the reason in finding 4 above,
and both were proven capable of failing before being proven capable of
passing (the harness-can-fail discipline this arc inherited from
`perf_budget.rs` and extended to every new gate, including one live,
real, CI-confirmed regression-and-revert cycle for the M6 gate
specifically — not only the unit-test-level synthetic proof).

**The second contract, measured honestly.** Pre-arc baseline: **6m34.0s**
real, `cargo test --workspace --release`, captured before M1. Getting
a trustworthy post-arc number took three attempts, and the reason each
attempt failed is itself worth recording rather than smoothing over:
the first run rebuilt several crates from scratch because a mid-session
container restart had reset the build cache, and the second run also
rebuilt from scratch because this same milestone's own version bump
(0.28.0 → 0.29.0) invalidated every crate's cached artifact — both
runs measured cold-build time, not this arc's actual effect, and both
were discarded rather than reported as the answer. The third run
finally had a warm build cache, so its 41s was genuine run time rather
