# CIaC v0.32-file — Spending the Instrument: The Optimization Arc (implementation plan)

> Implementation plan. Document number ≠ release number (standing
> precedent; expected to ship as **0.30.0**). Assumes
> `31UpdatePlan.md` shipped as 0.29.0. That arc was instrument-only —
> it built `ciac-bench`, the committed `docs/perf/baseline.json`, the
> callgrind and scaling gates, and a ranked twelve-item inventory
> mapped against those instruments. It changed no compiler behavior
> and shipped no optimization. This arc is the other half: it
> implements all twelve items, and every milestone is a measured
> before/after against the committed baseline, with rollback as a
> pre-registered, first-class outcome rather than an embarrassment.
>
> **Byte-identity contract:** every generated byte, on every target,
> for every example, is identical before and after this arc. This is
> the inverse of `31UpdatePlan.md`'s own contract and it is stronger:
> that arc promised not to touch the compiler at all; this one touches
> the compiler in nearly every milestone and promises the *output*
> cannot tell. The enforcement mechanism is unchanged from that arc:
> the 145 golden snapshots
> (`tests/tests/snapshots/golden__gen__{python,rust,typescript,go,java}__*.snap`),
> `determinism.rs`, `conformance.rs`, `openapi.rs`, `golden.rs`, the
> `tests/ui/` negative corpus, and `scripts/sim-corpus-x5.sh` (50
> program×target combinations that *execute* generated code rather
> than merely diffing it). If any of these moves, the milestone stops
> and the cause is investigated as a defect before anything else
> proceeds.
>
> **Second contract — no metric may regress to buy another.** A
> milestone that improves its own named metric while pushing another
> outside its noise band is a trade, not a win, and the trade must be
> stated and accepted explicitly, never discovered later.
> `ciac-bench --compare` reports every metric it knows about, not only
> the one a milestone targets, precisely so a silent trade cannot hide
> in the parts of the report nobody was looking at.
>
> **Rollback is graduated, pre-registered before any code exists.**
> Revert on any correctness failure, any generated-byte change, any
> metric regression outside the noise band, or a measured gain under
> half its pre-registered threshold. Between half and full threshold:
> keep the change, record the shortfall in the milestone report and in
> this document's own running log. A reverted milestone is a *result*
> of the arc, not a failure of it — exactly the posture
> `31UpdatePlan.md` M5 took toward dropping a gate outright.
>
> **Confidence:** high on items 1, 2, 4 (each is a small, mechanically
> verifiable change with a narrow blast radius); moderate on item 3
> (allocation reduction is real but its ceiling is unmeasured until
> M7's DHAT run); moderate-to-low on item 10 (the fix is structurally
> obvious — bare `Vec`s with zero indexes — but graph mutation sites
> must be audited exhaustively or an index goes stale silently, which
> is a correctness bug wearing a performance patch's clothes); genuine
> unknown on item 11 (Java formatter cost may be an unmovable JVM-
> startup floor, and this document says so before finding out, not
> after). Every threshold below was set from numbers measured in
> `31UpdatePlan.md`'s own session, on this machine (4 vCPU, no SHA-NI)
> — ratios are expected to travel to other hardware, absolutes are not.

### What was verified against the actual code before this plan was written

Three headline numbers from the motivating investigation were checked
against source, not re-taken from a profile, because a plan built on a
profile nobody re-read is exactly the failure mode `31UpdatePlan.md`
exists to prevent:

- **Item 2 is real and precisely two redundant passes, not three.**
  `regen.rs:105-106` computes `disk_hash` (over on-disk bytes) and
  `new_hash = hash_content(generated)` (over the freshly generated
  string) inside `plan_regeneration`. `manifest.rs:118`
  (`build_manifest`) then calls `hash_content(content)` again over the
  *same generated string* on the same build. The disk-hash pass is
  load-bearing — it is how a `Conflict`/`SeededDrift`/`Update` is
  detected at all — so only the generated-content hash is doubled, not
  tripled. `docs/perf/baseline.json`'s callgrind demonstration
  (`31UpdatePlan.md` M6, reverted at `c9aa060`) measured one *added*
  redundant pass at **order-system +15.09%** instructions; M2's
  threshold below is set at half that, since removing the existing
  double is a smaller change than adding a third would have been.
- **Item 3 is unconditional cloning, confirmed at the two exact
  lines.** `regen.rs:109-112`: `generated_content` clones every
  file's generated string and `disk_content` clones every file's disk
  bytes as a lossy UTF-8 string, for *every* entry regardless of
  status — including `Unchanged`, which never renders a diff and
  writes nothing. `sim-three-service`/typescript alone is 806 KB of
  generated output per build (`docs/perf/codegen-baseline.md`).
- **Item 10's target has literally zero indexes**, confirmed reading
  `graph.rs:169-185`: `SystemGraph` is nine bare `Vec`/`bool` fields.
  `find_named_in_service` (`graph.rs:353-361`), `edges_from`/`edges_to`
  (`:363-369`), and `pipeline_of` (`:372-373`) are linear scans, called
  from inside loops at roughly 47 sites across `ciac-sema` and
  `ciac-codegen`. `perf_scaling.rs` measured `sema::analyze` growth at
  1.93×/2.80×/2.72× across N=100/200/400 in `31UpdatePlan.md`'s own M7
  — below its 4.5× ceiling, but not the flat-ish curve indexing would
  produce, and `ciac check` at N=400 already spends 31.75% of
  instructions in `Vec::from_iter` and 12.28% in
  `find_named_in_service` per that arc's M8 callgrind breakdown.
- **`environment()` eagerly parses every template on the first
  `generate()` call, and `cached_environment` (added `30UpdatePlan.md`
  M4) does not change that for a CLI process.** `template.rs:39-41`'s
  `for (name, source) in templates { env.add_template(name, source)?; }`
  runs inside `environment()`, which `cached_environment` calls exactly
  once per backend per process via `OnceLock::get_or_init`
  (`template.rs:74`). The `OnceLock` amortizes cost *across* calls
  within one process — it does nothing for a `ciac build` CLI
  invocation, which calls `generate()` once and exits. Root
  `Cargo.toml:57` already has `minijinja = { version = "2", features =
  ["loader"] }`, confirming the lazy-loading path (`Environment::
  set_loader`) is a supported swap on the already-pinned dependency,
  not new machinery.

## Pillar 1 — Every threshold is pre-registered before its milestone's code exists

`31UpdatePlan.md` Pillar 1 derived gate bands from measured noise
before choosing them, specifically to prevent a band being picked to
fit whatever the data turned out to say. This arc applies the same
discipline one level up: each milestone below states its threshold in
this document, before that milestone's implementation commit, and the
graduated-rollback table in the preamble is the enforcement — not
discretion at milestone-close time.

## Pillar 2 — The suite runs at every milestone boundary, not just at the end

The full sequence below runs twice per milestone: once immediately
before the milestone's first commit (confirming a clean starting
point, since a milestone that starts from an already-broken tree
cannot attribute a failure correctly), and once after the milestone's
work lands.

```sh
cargo test --workspace
git status --porcelain -- tests/tests/snapshots/     # must be empty
find . -name '*.snap.new' -not -path './target/*'    # must be empty
scripts/sim-corpus-x5.sh                             # 50 combos, all PASS

cargo build --release -p ciac
cargo run --release -p ciac-integration-tests --bin ciac-bench -- \
    --compare=docs/perf/baseline.json --with-callgrind --with-scaling
cargo test -p ciac-integration-tests --test perf_budget
cargo test -p ciac-integration-tests --test perf_baseline -- --ignored
cargo test --release -p ciac-integration-tests --test perf_scaling -- --ignored
scripts/bench-codegen.sh
scripts/bench-callgrind.sh --metric allocations
```

M8 additionally runs `--with-verify --with-slow-tests --with-sim`,
since those arms cost real minutes and are the milestone's own
subject rather than routine overhead every other milestone would pay
for nothing.

## Pillar 3 — Two baselines, deliberately, so no delta is ambiguous

- **`docs/perf/baseline-v0.29.0.json`** — a frozen copy taken at M1,
  never rewritten again for the rest of this arc. Every milestone's
  *cumulative* delta is measured against this file.
- **`docs/perf/baseline.json`** — updated after each *proven*
  milestone (one that was kept, not reverted), so the next milestone's
  `--compare` shows that milestone's own *incremental* delta rather
  than the whole arc's. Every `--update-baseline` carries a
  justification in its commit message, continuing the discipline
  `docs/perf/README.md` already states.

Conflating these two views is how an arc loses track of which change
bought which win; keeping both is the fix.

## Pillar 4 — Graph indexes are additive-only and change no public signature

M6 is the milestone most able to break something silently — a stale
index produces a wrong answer, not a crash. The discipline: every
accessor's public signature (`find_named_in_service`, `edges_from`,
`edges_to`, `pipeline_of`) is unchanged, so all ~47 call sites need no
edits and no review beyond "does the index agree with a linear scan."
Every mutation path into `nodes`, `edges`, `pipelines` is enumerated
and updated in the same commit that adds the index it would otherwise
invalidate — never added in a follow-up.

## Pillar 5 — `source_hash` early-out fails closed, never open

M3 changes `ciac build`'s default behavior for the first time in this
arc: a warm no-op build can now exit without regenerating. The one
unacceptable failure mode is skipping a build that should have run. The
early-out therefore requires *agreement* — manifest present, recorded
`source_hash` equal to the current source hash, recorded `BuildRecipe`
equal to the current invocation's flags, and the manifest's recorded
file set intact on disk — and falls through to the full path the
moment any of those is missing, mismatched, or merely a legacy
manifest with no recipe at all. `--force` always bypasses the check.

## Pillar 6 — The Java formatter's cost may be a floor, and this arc says so upfront

Item 11 is the one item in the inventory whose fix is not already
known. `30UpdatePlan.md` M2 already batched Java formatting to one JVM
invocation per `generate()` call, which means the 1.34 s measured for
`order-system` is dominated by JVM startup, not per-file formatting
work — a floor no amount of clever batching inside a single-invocation
model can push below. M7 investigates in the stated preference order
(skip-when-canonical, reuse-one-JVM-across-process,
persistent-daemon-rejected-in-advance) and is explicitly permitted to
conclude the floor cannot be moved without a stateful daemon this arc
has already decided against building.

## Pillar 7 — The checkpoint has real teeth

M5 is a hard serialization point: nothing in M6, M7, or M8 starts
before M5's own commit lands, exactly as `31UpdatePlan.md` M5 gated
M6-M9. Its four pre-registered outcomes include "the arc stops here,"
stated as a legitimate success rather than a fallback, mirroring
`30UpdatePlan.md`'s own precedent for the same decision.

## Milestones

1. **M1 — The frozen "before."** No optimization. Copy
   `docs/perf/baseline.json` to `docs/perf/baseline-v0.29.0.json`,
   immutable for the rest of the arc. Regenerate `docs/perf/
   baseline.json` on current HEAD (post-0.29.0-bump), so the arc
   starts from a same-session, same-machine reading rather than one
   carrying `31UpdatePlan.md` M9's own `git_sha`. Run the full Pillar-2
   suite once to confirm a clean starting point and that every
   instrument still works after the version bump. Record the pre-arc
   `cargo test --workspace --release` wall time (`31UpdatePlan.md` M9
   measured 5m21.136s) as this arc's own reference for M8/M9. Write
   this document's own running log skeleton (below).

2. **M2 — Hash once, not twice.** `plan_regeneration` already computes
   `new_hash` for every file; thread it out of `RegenEntry`
   (`regen.rs:39-46`, add a `new_hash: String` field alongside the
   existing `new_content`) and have `build_manifest` accept a
   precomputed `BTreeMap<String, (FileRole, String)>` of path→hash
   instead of re-hashing `project.files_with_roles()` itself.
   `commands.rs` calls `build_manifest` from eight sites
   (`:329, 382, 487, 992`, plus the ones feeding `write_manifest`
   after a `plan_regeneration` call) — each is updated to pass the
   plan's own already-computed hashes rather than the raw project.
   **Threshold: ≥8% reduction in `ciac build` instruction count on
   `order-system`** via `ciac-bench --with-callgrind`. Existing
   `manifest.rs`/`regen.rs` unit tests (`manifest_is_sorted_and_stable`,
   `clean_owned_file_updates`, etc.) must pass unmodified — they
   exercise the hash-comparison logic, not its call count, so a correct
   threading change does not need them touched.

3. **M3 — The `source_hash` early-out.** In `cmd_build`'s path through
   `commands.rs`, before generation: if a manifest loads, its
   `source_hash` equals the freshly computed source hash, its `recipe`
   is `Some` and equal (field-by-field) to the current invocation's
   `BuildRecipe`, and every path in `manifest.files` exists on disk
   with a matching hash — print `up to date, nothing to do` and exit
   `ExitCode::SUCCESS` without calling `build_system`, `generate`, or
   `plan_regeneration`. `--force` skips the check unconditionally. Any
   missing manifest, `None` recipe (legacy manifest), hash mismatch, or
   missing/altered file falls through to the existing full path — never
   guesses. **Threshold: ≥5× on the no-op warm rebuild** for
   python/ping and go/sim-three-service, measured by
   `scripts/bench-codegen.sh`'s warm-rebuild column (M3 of
   `31UpdatePlan.md`). New CLI-level test coverage (mirroring the
   `tests/ui/` harness style): skip fires on an untouched tree;
   `--force` always regenerates; editing a generated file on disk
   defeats the skip; deleting a manifest-tracked file defeats the skip;
   a manifest with `recipe: None` always falls through; changing
   `--deploy`/`--client` between builds defeats the skip.

4. **M4 — Lazy template loading.** Replace `template.rs:39-41`'s
   `for (name, source) in templates { env.add_template(name, source)?; }`
   with `env.set_loader(move |name| { ... })` closing over the same
   `(name, source)` pairs backends already pass in via `include_dir!`
   (a `HashMap`/slice lookup, returning `Ok(Some(source.to_string()))`
   or `Ok(None)`). minijinja parses and caches each template on its
   first `get_template`, so steady-state rendering is unaffected and
   unused templates are never parsed at all. `cached_environment`'s
   `OnceLock` wrapper (`template.rs:69-82`) is unchanged — it still
   builds one environment per backend per process; the loader changes
   *what building means*, not *how often it happens*.
   **Threshold: ≥40% reduction in `template_setup` for python, rust,
   and typescript** (baseline: 1990.7 / 2205.3 / 2493.7 µs). Go's
   4157.9 µs is expected to move less, since a meaningful share is
   `gofmt` subprocess cost rather than parse time — tracked but not
   gated. Java's near-zero `setup_us` (JVM dominates its total) is
   excluded from the threshold; its reading not moving is itself the
   check.

5. **M5 — CHECKPOINT: cumulative measurement, go/narrow/stop.** No new
   code. Run the full Pillar-2 suite and compare cumulative M2+M3+M4
   gains against `baseline-v0.29.0.json`. Write the decision into
   `docs/perf/README.md` in a new section alongside `31UpdatePlan.md`'s
   own gate-decision writeup. **Pre-registered outcomes:** (a) M6-M8
   proceed exactly as planned; (b) M6 is narrowed to the IR-index half
   only, dropping the `build_system` dedupe, if M2-M4 already cleared
   the arc's own aggregate target; (c) M7's Java-formatter half (item
   11) is cut here rather than attempted, if the cumulative gain
   already justifies closing the arc without it; (d) the arc stops at
   M5 and ships M1-M4 as the release. Outcome (d) is a success of the
   checkpoint, not a shortfall of the arc — the same framing
   `30UpdatePlan.md` M5 used for stopping early. **Hard serialization
   point: no commit under M6, M7, or M8 lands before this milestone's
   own commit.**

6. **M6 — IR indexes (the quadratic) and `build_system` dedupe.** The
   arc's highest-risk, highest-value milestone. Add to `SystemGraph`
   (`graph.rs:169-185`): a `HashMap<(ServiceId, NodeKind, Option<Arc<
   str>>... )>`-shaped or equivalent lookup behind `find_named_in_
   service`; adjacency maps (`HashMap<NodeId, Vec<EdgeId>>` for
   from/to) behind `edges_from`/`edges_to`; an owner map
   (`HashMap<NodeId, usize>` into `pipelines`) behind `pipeline_of`.
   Built once, incrementally, at every push into `nodes`/`edges`/
   `pipelines` — `add_node_owned` (`:199-213`), `add_edge`
   (`:236-247`, note its existing dedupe-on-insert semantics must be
   preserved exactly), and wherever `pipelines.push` occurs
   (`ciac-sema`'s builder, outside this file — audited, not modified,
   since `pipelines` is a `pub` field pushed to directly). No public
   signature changes; all ~47 call sites untouched by construction.
   Separately, dedupe the three `build_system` calls
   (`commands.rs:2598, 2701, 3161`) that can occur within one logical
   build by threading a single computed `SystemModel` through instead
   of recomputing it per call site that needs one.
   **Threshold: `sema::analyze` growth ratio ≤2.5×/doubling** at
   N=100/200/400 (measured 1.93/2.80/2.72× pre-arc; `perf_scaling.rs`'s
   own ceiling is 4.5×, so this is a tightened, arc-specific bar, not
   the gate's own), **and** ≥25% reduction in `ciac check` instruction
   count on a synthetic N=400 corpus via `--with-callgrind`. If indexes
   land but the ratio does not move, that is a revert: the diagnosis
   was wrong and the added complexity has no return.

7. **M7 — Regen allocation reduction and the Java formatter.** Stop
   `regen.rs:109-112` cloning `generated_content` and `disk_content`
   unconditionally: restructure `RegenEntry::old_content`/`new_content`
   population so an `Unchanged` entry (which never renders a diff and
   is never written by `apply_regeneration`) does not allocate either
   string — compute them only for entries whose eventual `status`
   needs them (`New`, `Update`, `Conflict`, `SeededDrift`, and
   `OrphanDelete`/`OrphanLeft` for their existing `old_content` use).
   **Threshold: ≥20% reduction in DHAT total bytes** for `order-system`
   (baseline 2,756,891 bytes / 16,594 blocks) via
   `scripts/bench-callgrind.sh --metric allocations`. Separately,
   investigate the Java formatter's per-`generate()` JVM cost (1.34 s
   on `order-system` vs. python's 1.29 ms) in preference order: (i)
   skip invoking the formatter when template output is already
   canonically formatted, verified against the existing goldens with no
   new machinery; (ii) reuse one JVM across the whole compiler process
   rather than one per `generate()` call; (iii) a persistent formatter
   daemon, rejected in advance per Pillar 6. **Pre-registered: item 11
   may be cut at M7 with the reason recorded**, and cutting it does not
   fail the milestone — the allocation work stands independently.

8. **M8 — Validation and test-suite orchestration.** No compiler code,
   no generated-output risk — the reason this milestone is scheduled
   last among the implementation milestones rather than first.
   Parallelize `validate_generated` (`commands.rs:3521-3538`) across
   independent projects, and across a target's own `validate` steps
   where the target declares them order-independent.
   **Threshold: ≥30% wall-clock reduction on multi-project examples**
   via `ciac-bench --with-verify`. Point generated Rust projects at a
   shared `CARGO_TARGET_DIR` (env var passed through the verify
   subprocess) so repeat `verify` runs reuse compiled dependencies —
   rust's 116.55 s is essentially all `cargo test` cold-compiling from
   scratch today. Split `determinism.rs` and `openapi.rs` (one
   `#[test]` fn each today) into per-target or per-example test
   functions so libtest's own thread pool can parallelize what is
   currently a single serial block.
   **Threshold: ≥30% reduction in combined slow-binary wall time**
   against the 210.3 s `31UpdatePlan.md` M8 reading (determinism 74.22
   + conformance 65.03 + golden 35.61 + openapi 35.46). Add a
   `[profile.dev]`/`[profile.test]` stanza tuned for test throughput
   (`opt-level` on dependencies via `[profile.dev.package."*"]`,
   `debug = "line-tables-only"`), kept only if `cargo test --workspace`
   beats the M1-recorded 5m21.136s reference; reverted otherwise.
   Measured with `--with-verify --with-slow-tests --with-sim`.

9. **M9 — Tighten the ratchet, promote what soaked, docs, retrospective,
   version 0.30.0.** Revisit `perf_budget.rs`'s 1000× multiplier now
   that this arc has moved the numbers it was calibrated against —
   re-derive in the **debug** profile `cargo test --workspace` actually
   uses, per `31UpdatePlan.md` M9's own finding that the multiplier is
   profile-sensitive, never in `--release`. Evaluate `perf_baseline.rs`
   and `perf_scaling.rs` against `docs/perf/README.md`'s existing
   promotion checklist; promote only a gate that has genuinely
   accumulated its pre-registered 20-merge soak with zero spurious
   fires (expected: neither has, since this arc — like `31UpdatePlan.
   md` — runs in one continuous session; the "Promotion status" table
   is updated with the real count and left honest rather than
   fabricated). Regenerate `docs/perf/baseline.json` as the arc's final
   reading. Bump 0.29.0 → 0.30.0 across the file set the
   `3d13581`/`6a97001` precedent fixed: root `Cargo.toml`
   `[workspace.package]` plus its internal-crate version pins,
   `Cargo.lock` (regenerate), `docs/language.md`, `docs/positioning.md`,
   `docs/targets.json` (regenerate via `ciac targets --json`),
   `editors/vscode/package.json`. Append the retrospective to this
   document: the cumulative before/after table against
   `baseline-v0.29.0.json`, which milestones were reverted and why,
   which thresholds were met versus merely approached, and an honest
   note on whether pre-registration survived contact with the data.

### Per-milestone exit checklist

Every milestone, without exception, before its commit is considered
shipped:

- `cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings`
- `cargo test --workspace` green.
- **Byte-identity check.** `git status --porcelain -- tests/tests/snapshots/`
  empty; zero `*.snap.new` files; `scripts/sim-corpus-x5.sh` all PASS.
  If any is false, the milestone stops and the cause is investigated as
  a defect before anything else proceeds.
- **Threshold check** against this document's own pre-registered number
  for that milestone, via the Pillar-2 suite.
- **Graduated-rollback decision recorded**, even when the outcome is
  "kept, threshold met" — a milestone report with no explicit pass/fail
  statement is the failure mode this arc's whole discipline exists to
  avoid.
- Numbers land in `docs/perf/baseline.json` (when the milestone is
  kept) or the revert commit's message (when it is not) — never only
  in a chat transcript.

```
                    │                       ├──▶ M7 ──┼──▶ M9
                    │                       └──▶ M8 ──┘
```

M2 precedes M3 deliberately: once M3's early-out skips the warm path
entirely, M2's own benefit on that path becomes unmeasurable, so M2's
number must be taken before M3 lands. M4 is independent of both and
may run concurrently with either. M5 is a hard serialization point.
M6, M7, and M8 are mutually independent of each other.

## Explicit cuts

- **No new gates.** `31UpdatePlan.md` built three; this arc consumes
  them and tightens one (M9). A fourth gate while two are still
  unpromoted would be gate inflation the promotion checklist was built
  to discourage.
- **No SHA-NI-specific work.** The 39.79% hashing figure is from a
  machine without it; `sha2` already dispatches at runtime to hardware
  acceleration when present. Hashing *less* (M2) is portable across
  every machine this compiler runs on; hand-tuning the hash itself is
  not, and is out of scope.
- **No parallel code generation.** `generate()` is 0.5-1.3 ms for four
  of five backends; threading it would add failure modes to a CLI
  process to buy microseconds nobody will notice.
- **No incremental compilation of `.ciac` sources.** The front end
  (`ciac-syntax` + `ciac-sema`) is 146 µs on `order-system`. M6 fixes
  the growth curve of the expensive part; nothing in this arc's
  findings warrants a dependency-tracked incremental front end.

## Risks

- **M6 is the one that can break things silently.** An index gone
  stale after an unaudited mutation path produces a *wrong* lookup, not
  a crash — the worst failure shape for a compiler's own correctness.
  Mitigation: every push into `nodes`/`edges`/`pipelines` is enumerated
  before a single index line is written; `sim-corpus-x5.sh` executes
  generated code rather than diffing it, which is the strongest
  available proof that a wrong lookup did not silently change program
  behavior.
- **M3 changes default CLI behavior for the first time in this arc.**
  A too-eager skip — a user's real edit not triggering a rebuild — is
  the worst possible failure mode for a compiler. Mitigation: the
  early-out requires manifest + `source_hash` + recipe + file-set
  agreement and falls through on any doubt; `--force` always works
  regardless of what the check concludes.
- **Every threshold in this document was set from data, but before the
  code that must clear it exists.** The graduated-rollback rule in the
  preamble is the mitigation; M5 is the place to admit early if a
  threshold was optimistic rather than discovering it only at M9.
- **This machine has 4 vCPUs and no SHA-NI.** Ratios are expected to
  travel to other hardware; absolute timings are not, and this
  document says so rather than implying a universal measurement.

## Verification strategy

- Pillar 2's full suite at every milestone boundary, before and after,
  with results recorded per the exit checklist.
- `scripts/sim-corpus-x5.sh` at every milestone — the strongest
  available byte-identity proof, since it executes generated code
  rather than only diffing it.
- `mcp__github__actions_*` (or the equivalent CI check) polled to a
  terminal state after every push; any pre-existing known-failing job
  is disclosed and excluded from being treated as a new failure, and
  any genuinely *new* failure is a rollback trigger per the graduated
  table.
- M9: cumulative delta against `baseline-v0.29.0.json`; `cargo test
  --workspace --release` timed against the M1-recorded 5m21.136s;
  `grep -rn '0\.29\.0'` across `.toml`/`.json`/`.md` to confirm no
  stray version reference survives outside historical plan files.

## Confidence and handoff

This document is written before M1's own commit, per the standing
precedent that a plan is authored whole and then executed milestone by
milestone, not discovered as it goes. Every threshold above is a
number chosen before the code that must clear it exists; the running
log and M9's retrospective are where this document is honest about
which of those numbers survived contact with reality.
